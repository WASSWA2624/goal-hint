# Goal Hint feature audit

Updated: 31 October 2026 (Africa/Kampala). Scope: [audit prompt](prompts/goal-hint-feature-audit.md). The report-only audit used source baseline `706b96c9`; the approved Subscriber dashboard implementation started from clean `bdcb66e5` on `main`. Other feature findings retain the earlier audit scope.

**Custom Filters and the approved Subscriber dashboard subscription/activity scope are implemented in source. The main remaining gaps are the two-session policy, referral rewards/invitations, in-app notifications and mobile sharing.** The dashboard extends the existing Account page; referral statistics and earned-day balances remain deferred until their ledger exists.

Statuses describe repository implementation, not a verified production deployment. Production schema/grants, real database races, messaging delivery, provider accuracy and signed physical-device behavior remain **Unable to Verify**. Missing means no implementation was found in the inspected application routes, services and models; external hosting systems were not inspected.

The following approved changes supersede the original configuration UI requirements: management lives only in Slip Builder, with no separate account-page manager; dates are not saved; saved times load for today; selecting an option does not apply it until **Use Selected Filter**. Row 1 is assessed against that approved scope. The original dashboard-management criterion is therefore intentionally excluded, rather than treated as an outstanding defect.

## Key risks

- **Custom Filters deployment remains a release gate.** The [migration](next-js/prisma/migrations/20261031040514_saved_slip_configurations/migration.sql), [MariaDB overlay](next-js/prisma/mariadb/20261031040514_saved_slip_configurations.sql) and [application grants](next-js/docs/deployment/slip-configuration-grants.sql) exist. Their deployment and genuine database lock/index behavior are unverified. A complete UI and mocked transaction tests do not establish those facts.
- **Cross-device persistence and concurrent access differ.** Configurations belong to the account and survive logins, but a second authenticated login currently revokes the first. The remaining session-policy defect must not be described as missing configuration persistence.
- **Rewards need secure accounting and access ordering.** Award once per eligible verified new registration, without payment/lifetime-cap conditions. Neither registration trials nor money credit substitute for earned days. Credit auto-renew can queue paid access before expiry, so reward consumption needs an explicit priority policy.
- **Sharing promises exceed current recipient access.** The [public-link copy](next-js/src/i18n/messages/slip-sharing.ts) promises anyone can view selections; the service withholds active selections without entitlement. Align copy/landing while preserving the gate. Already distributed images cannot be revoked by subscription changes.
- **Runtime/data confidence is limited.** Proxy trust, message receipt, provider truth, evaluation approval and release signing were not checked live. Synthetic demo metrics and hypothetical fixed-unit aggregate returns are not verified production quality or personal betting results. Live reads may seed demo data or renew access, so no live application/database requests were made for this refresh.

## Dependencies and unanswered questions

- **Resolved configuration decisions:** builder-only management; Create/Rename/Update/Delete plus Use Selected Filter; dropdown selection is staged; time ranges are saved but dates load as today in Africa/Kampala; blank saved times mean 00:00–23:59. An optional default fills a fresh visit without query parameters, with interaction/explicit-query safeguards. Management uses account access even after subscription expiry/closed sales. These are no longer unanswered design questions.
- **Referral eligibility:** attribution expiry and first/last eligible link rules, treatment of existing/unverified accounts, phone changes/merges/erasure, and narrowly scoped fraud review/reversal still need decisions. Preserve unlimited valid accumulation and exactly-once awards.
- **Access ordering:** specify queued paid periods versus earned days versus credit auto-renew, including a paid purchase during earned access and preservation of unused valid rewards.
- **Sessions:** clarify whether phone authentication requires phone/password on a verified account or a fresh OTP per new login/device, and whether administrators follow the same two-session limit.
- **Notifications/sharing/data:** define relevant result/account events, intended access to active shared links, individual-prediction sharing scope, required player-data coverage/rights, approved performance policy and market/reporting windows. Deployment/worker/device checks require a suitable environment and separate authorization.

## Recommended implementation order

The subscription/activity portion of the Subscriber dashboard has now been delivered under separate approval. Remaining recommendations:

1. **Validate the delivered Custom Filters release:** deployed migration/grants, genuine database integration, ownership and persistence across sign-out/devices. Keep the approved builder-only interface and explicit application behavior.
2. **Correct the two-session policy:** atomic oldest-session eviction at third login. Qualify the delivered Account page's active-package and payment/access summary against deployed storage.
3. **Implement referral identity, eligibility and earned-day accounting:** exactly-once verification rewards, abuse controls and paid/earned/credit ordering before showing a spendable balance.
4. **Add subscriber referral statistics and Invite Friends:** quiet account/menu entry points, personal-link copying, WhatsApp/Telegram/native sharing using the approved ledger.
5. **Add essential in-app notifications and targeted sharing fixes:** access/reward events first; reuse current slip sharing on phones and resolve restricted-recipient messaging without weakening access controls.
6. **Qualify match/performance data and mobile release journeys:** representative data reconciliation, approved metric binding, necessary player-data coverage and physical-device sharing/deep-link tests. Preserve existing screens and defer detailed production load work.
