# Flutter app shell

Build the minimal Flutter shell in the repository-root `flutter/` directory for the existing Next.js web app in `next-js/`, preserving the separate project directories and the web development workflow. Central URL configuration, browser adapters for Android/iOS/macOS/Windows, and installed identity/white startup feedback are implemented. Shared web code implements the anonymous offline cache, verified reachability, bounded retries and safe cache updates. Remaining platform qualification, Linux embedding and release acceptance follow [the Flutter development plan](../flutter/dev-plan/000-index.md) and [the tracker](../flutter/dev-tracker.md). Keep each app's numbered development files in its own `dev-plan/` folder, with shared specifications and prompts at the repository root.

- Support installable Android, iOS, Windows, macOS, and Linux builds through suitable embedded web views and minimal reusable platform adapters.
- Keep all screens, navigation, business logic, and application features in `next-js/`. Flutter should only host the web app and provide necessary platform integration, avoiding duplicate implementations.
- Use one central development/production URL configuration. Development must support localhost where appropriate and a reachable host address for emulators or physical devices. Production must use the deployed HTTPS URL. Document how to configure each environment.
- Support cable-free Android development: load web content directly over the LAN and use Android's paired wireless ADB for deployment/debugging. Keep pairing codes and keys out of the repository.
- Reuse the branding sources in `next-js/assets/brand/` and exported assets in `next-js/public/brand/`. Use the display name **Goal Hint** and its actual logo, with no Flutter starter artwork or dark launcher tile. Use transparency where supported and white where an opaque layer is required. The launch/loading screen must be white in both OS appearances, show the app name and logo, and provide loading animation with reduced-motion support. Product styling and theme remain web-controlled. Reuse established components, avoid added rounded corners, and apply each safe-area inset once.
- After at least one successful online load, persist the app assets and permitted previously loaded content needed to start and display the last working cached app without internet, including after closing or restarting the app. Do not rely solely on an in-memory web view or a screenshot. Keep offline behavior in the shared web code wherever possible, adding only necessary platform support.
- When connectivity returns, check that the server is reachable, refresh content and cached assets, and safely apply available updates. Preserve the last working cache if an update fails and avoid interrupting active user input. Offline access covers cached content; server-dependent actions require connectivity. Provide a clear first-launch offline state when no cache exists, and respect authentication and logout when caching user-specific content.
- Run web commands from `next-js/` and Flutter commands from `flutter/`. Use efficient, professional, reusable code and minimal maintained dependencies. Preserve existing repository changes. Document setup, development URLs, platform build requirements, offline behavior, and limitations. Verify online launch, offline cold start, reconnection updates, and failed-update recovery on each supported platform; clearly identify any platform that could not be tested.

Normal web UI and business-logic updates must be delivered through Next.js without rebuilding the Flutter shell; native integration or configuration changes require a new Flutter build.
