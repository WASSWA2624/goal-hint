# Register members with an automatic introductory trial

Implement this change in the Goal Hint Next.js app. Let a regular member register with a mobile phone number and password, get a usable account immediately, and sign in again with those credentials. Public registration requires neither administrator approval nor an outbound activation or verification message. If the new account qualifies, start its one-time introductory trial as part of registration.

## Current source behavior

- Public registration validates the phone and password, records trial eligibility and referral attribution, and returns a restricted session. Auth and page handlers route that session to account verification. Password login for an unverified number also returns a restricted session, and changing the number currently re-enters verification.
- A verified member can explicitly activate the configured trial through `POST /api/account/trial`. The access service uses the same account lock for activation and the first paid grant. A first paid grant forfeits an available unused trial. During an active trial, the full paid term follows the trial.
- Signup verification can send a code by SMS or WhatsApp. On successful verification the server stamps `phoneVerifiedAt`, evaluates the referral award, and enqueues a welcome message. Forgotten-password recovery has its own code purpose and restricted session.
- The screenshot shows a seven-day offer. Read the current settings on the server because duration and whether a trial is offered are configurable. The source and repository notes describe the baseline for this work. Verify any claims about a deployed release against that release separately.

## Implementation requirements

### Account entry and recovery

- Require only the phone number and password. Preserve number normalization and validation, unique-number and reserved-administrator safeguards, password hashing and rate limits, same-origin checks, private cookie handling, and normal auth destinations, including the canonical shared-slip return. Remove any signup delivery requirement tied solely to sending an activation code. Handle recovery channel availability in the recovery flow.
- Return a normal authenticated regular-member session when registration commits. Confirm normal password login, Account and session API reads, and prediction access with an active trial. Audit all `phoneVerifiedAt` consumers, including the viewer-access query and private member routes. Use the appropriate server-side account and session checks for member admission and entitlements. Keep actual ownership proof required wherever it represents a distinct privilege or protection. Preserve administrator authentication, blocked and erased account restrictions, restricted reset sessions, session revocation, and the two-device limit.
- Keep `phoneVerifiedAt` truthful and bound to the current number. A submitted number, account registration, and a password login provide no proof of phone ownership. Preserve the setting that explicitly allows verified members access without a subscription and review any other security-sensitive verification gates individually.
- Confine outbound member account messages to forgotten-password recovery. Trace direct delivery and queued messages, including the old signup code and welcome message, so login, signup, or a phone-change redirect cannot reintroduce an activation message. Check queued and in-flight legacy messages as part of the transition. Keep legitimate in-app confirmations, errors, and payment/access/referral status. Preserve secure recovery with generic public responses, scoped and time-limited single-use codes, throttles, reset-only access, and session rotation.
- Review the phone-change flow end to end. Retain the current-password check, collision and reserved-number checks, and protections against takeover and stale recovery codes. Changing the phone must clear any ownership proof for the old number. Confirm how a new recovery number can be bound safely under the recovery-only delivery rule. If the current policy requires separate proof before a change can take effect, resolve the permitted transition with the owner before weakening that requirement.

### Trial award and historical data

- Use the current authoritative settings and `offeredTrialDays`, including zero days, paywall Off, and the verified-member access setting that suppresses new trial offers today. Use server time for the start and end of the period. A deliberately disabled offer still permits account creation.
- Reuse the existing audited access-period creation, eligibility and trial-history checks, and account/settings locking conventions. Commit the account, eligible grant, and associated registration state consistently with session issuance. If a required settings read or write fails, roll back the incomplete registration so the member can retry safely. Protect against normalized duplicate numbers, concurrent requests, and a retry after commit with an uncertain response. Keep the existing duplicate behavior or guide the member to sign in without replacing credentials, issuing a session to the duplicate request, or starting another trial.
- Keep paid access, renewals, active and historical trial periods, forfeiture, and referral balances intact. Preserve the first paid grant's handling of any unused legacy eligibility and the ordering of paid time after an active trial. A later sign-in, recovery, phone change, settings change, or old trial request must not mint a trial for a new registration that already used its offer or signed up while it was disabled.
- Remove **Activate free trial** from the new-signup experience. Show the active period and expiry when relevant, and retain the existing inactive/expired or available-to-subscribe states as appropriate. Decide whether a legacy manual action and endpoint must remain for pre-change members with a documented unused offer. If retained, restrict that path on the server to the intended legacy cohort.
- Inspect how pre-change pending signups, pending phone changes, reset-only sessions, and administrator-provisioned accounts can be identified using durable data. Confirm each cohort's supported entry or recovery path and disposition of previously issued codes. Preserve existing access and active, expired, revoked, used, or forfeited trials. Resolve ambiguous legacy states before any backfill or session promotion. Apply automatic registration grants to eligible new signups only.
- Existing referral rewards require the actual first verification of the registered phone and recheck inviter eligibility. Preserve referral attribution, existing pending/awarded records, keyed phone history, and the one-award ledger rules. A signup or sign-in alone must never award days or mark the number verified. Check whether the approved proof path still exists under recovery-only messaging and how pending attributions should be handled. Password reset currently records genuine proof when completed and does not award the referral. Obtain a policy decision before making recovery an award trigger, granting rewards without proof, or changing existing referral eligibility.
