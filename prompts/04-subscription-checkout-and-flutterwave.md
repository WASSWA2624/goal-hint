# Restore subscription checkout and add automatic Mobile Money payments

An inactive signed-in member who taps **Unlock predictions** from a match should enter the existing subscription purchase flow whenever new checkout is available. Keep a safe return path to that match. Offer **Pay with Mobile Money**, or its localized equivalent, alongside the existing manual MTN MoMo and Airtel Money choices. Use Flutterwave as the underlying provider. Keep Goal Hint's checkout copy focused on Mobile Money and show any disclosures required by the provider.

## Trace checkout availability

- Follow the match unlock action into subscription checkout. Verify the signed-in member session, intended match destination, subscription route, active plans and usable payment methods. Reuse the application's local return-path validation across checkout, the Flutterwave handoff, status pages and return to the match. Preserve guest sign-in and account restrictions.
- `subscriptionCheckoutPublished` requires the paywall to be on. In production it also requires published terms and privacy notices and a configured public support contact. Both notices have `releaseReady: false` in this checkout. The subscription route separately handles settings and checkout-data failures and filters for active plans. The payment API also checks sales readiness. Diagnose the reported symptom through these conditions before changing navigation or UI.
- Distinguish local source findings from the deployed build, paywall mode, notice publication, support contact, active plans and method readiness in each environment. Verify deployed facts through authorized, redacted read-only evidence where available. Record missing evidence and the actual blocker. Resolve verified issues through the normal configuration and approved publishing path. Keep the gates in place, and obtain approved notice content and support details before representing them as published or configured. Deployment and live payment testing require separate authorization.
- Keep existing payment requests, in-app status, manual receipt submission and review, wallet credit and reservations, referral-day redemption and entitlement accounting working under their current rules, including when new sales are paused.

## Add the automatic Mobile Money flow

- After the member selects a package, display the amount in UGX and offer one action to confirm and start payment. Use the registered phone from the authenticated account server-side. Present it read-only and masked if useful for confirmation. Keep number entry and editing out of this flow. At initiation, revalidate the quote and account phone and require fresh confirmation if either changed. Preserve the existing checkout consent requirements.
- Start with the current Uganda Mobile Money direct-charge API reference. Its v3 example shows a provider authorization redirect. Confirm the matching authorization, webhook and verification contracts for the merchant's supported API version. Verify which networks and routing are supported for the actual merchant in staging, how to resolve MTN or Airtel reliably for the registered number, and which authorization mode and return behavior each network uses. If the merchant integration needs a network choice, resolve it before the final payment action without asking for another number. Use the supported authorization handoff, honor required navigation and disclosures, and document provider limitations. Only promise or use a direct push when the configured flow supports it. The customer enters their Mobile Money PIN only in the provider-controlled prompt or page. Goal Hint must never request, collect, proxy or persist a PIN.
- The documented v3 Uganda direct-charge endpoint requires customer email. Confirm a provider-supported approach that works for phone-only accounts and preserves the requested experience. Keep registration phone-and-password only, and never fabricate customer email. If the provider requires a significant additional checkout step or a change to collected customer data, record the dependency for the user's decision and leave the automatic option unavailable pending that decision.
- Confirm privately which existing merchant, shared merchant account or split subaccount is intended. The requested settlement destination is the owner's Mobile Money account. Verify the account, any authorized split, currency, provider capabilities and settlement route with the merchant and Flutterwave. Collecting a customer's UGX Mobile Money payment, settling to a subaccount and initiating a payout are separate operations. The split guide lists supported integrations and does not establish that the Uganda Mobile Money direct charge supports `subaccounts` or that the intended account can settle to Mobile Money. Confirm compatibility for the chosen collection path before enabling it. Verify the configured arrangement with sandbox evidence where supported, and record any settlement detail that needs provider or production confirmation. Use only supplied private identifiers and allocations. A new payout workflow or a different settlement recipient requires separate approval.
- Determine which fields of the supplied credential shape are required. The documented v3 Uganda direct-charge endpoint uses `secretKey` server-side, and webhook authentication uses `webhookSecret` according to the selected version's contract. Determine whether that flow uses `publicKey` or `encryptionKey` before requiring either. Keep credentials and routing and settlement configuration private, server-managed and environment-scoped. Keep sensitive values and personal contact details out of source, fixtures, documentation, public responses and logs. The current runtime policy recognizes staging slots for Flutterwave's sandbox secret key, webhook secret and webhook URL. This is configuration recognition only. The inspected source contains no provider checkout flow, and deployment readiness must be established separately.
- Gate charge initiation on an authorized member, server-side eligibility and availability, a current app-owned quote and a durable attempt with an app-generated unique reference. Bind the attempt to the member, registered number and network used, selected plan, amount, currency and validated return path. Derive the phone and amount server-side. Persist enough state to recover after a lost response and reconcile an uncertain attempt before retrying to avoid an unintended second charge. Determine how the new choice interacts with partial wallet or referral funding before exposing that combination. Preserve supported manual and internal funding choices and their accounting.
- Authenticate webhook requests with the contract for the selected API version. Treat webhook and browser return data as signals to verify through Flutterwave's server API. Check the verified final status, app reference, provider transaction identity, expected currency and amount against the stored attempt, with an explicit reconciliation rule for any mismatch. Only the rightful member should see private status or resume the purchase, including when a return requires sign-in. Show compact pending, success, failure and cancellation states without manual payment evidence for this method. An initiated or still-unverified charge stays pending even when the browser returns. Reconcile delayed confirmations or verification failures without granting access early.
- Reuse the established payment, wallet and entitlement services. Keep receipt identity unique and make allocation, funding debits and grants atomic and idempotent across retries, callbacks, concurrent or reordered events and restarts. Distinguish a first paid purchase from extension of existing access, including active trial and paid periods. Keep the scope to one-time subscription purchases and existing member-initiated renewal behavior. Recurring card billing and Flutterwave wallet top-ups are outside this request.

## Repository starting points

- Unlock and member navigation in `next-js/src/components/members/prediction-unlock.tsx`, `next-js/src/domain/subscriber-navigation.ts` and `next-js/src/domain/member-navigation.ts`. Checkout entry and controls in `next-js/src/app/_components/subscribe-route.tsx` and `next-js/src/components/members/{subscribe-controls,checkout-pay,payment-wizard,payment-status}.tsx`.
- Sales rules and runtime policy in `next-js/src/server/members/sales-readiness.ts`, `next-js/src/domain/{privacy-notice,terms-notice}.ts` and `next-js/src/server/config/runtime-policy.ts`.
- Checkout and accounting in `next-js/src/app/api/account/checkout/route.ts`, `next-js/src/server/members/{checkout,checkout-http,payments,wallet,access-codes}.ts`, and `next-js/src/server/admin/payment-review.ts`. Check the Prisma schema and MySQL/MariaDB migration conventions if persistent state changes are needed. See `next-js/docs/payment-checkout.md` and `APP_OVERVIEW.md` for existing behavior and release requirements.
- Provider references. Use the current Uganda direct-charge API for the Uganda integration. The general guide provides regional context. Examples from other regions do not establish Uganda requirements or behavior. The legacy Uganda guide may redirect or be unavailable. [Uganda Mobile Money direct-charge API](https://developer.flutterwave.com/api/charge/uganda-mobile-money), [General Mobile Money guide](https://developer.flutterwave.com/docs/collections-inflow/mobile-money), [Legacy Uganda authorization guide](https://developer.flutterwave.com/v3.0.0/docs/uganda). See also [Split Payments](https://developer.flutterwave.com/docs/split-payments), [Authentication](https://developer.flutterwave.com/docs/authentication), [Webhooks](https://developer.flutterwave.com/docs/webhooks), [Transaction Verification](https://developer.flutterwave.com/docs/transaction-verification) and [Settlements](https://developer.flutterwave.com/docs/payment-operations/settlements).

Keep navigation, the wizard and existing values mounted where their layout is fixed, preserve visible control labels and keep passive polling quiet. Update `APP_OVERVIEW.md` with implemented behavior, limitations and deployment status when implementing the change.
