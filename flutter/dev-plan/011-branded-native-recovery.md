# 011 — Branded native recovery

Replace engine connection-error pages with a bundled, themed native recovery
surface in the Android, iOS/macOS and Windows web hosts. This feedback works
without a connection or a previously cached website. The shared website and its
offline cache remain responsible for product screens and saved content.

## Presentation and identity

`NativeRecoveryView` reuses the shared `NativeErrorView` frame: bundled logo,
configured app name, themed status icon, a clear heading, a prominent retry
button and an icon-led checklist on a quiet surface. It uses square corners,
scrolls on short screens and supports enlarged text and reduced motion.

`AppBrandingScope` supplies the name and logo reference to loading, recovery,
configuration feedback and accessibility labels. The default name and palette
are generated by the existing artwork tool from the website's canonical
`next-js/assets/brand/brand-tokens.json`. `APP_DISPLAY_NAME` can override the
native feedback name at build time; embedding code can supply `AppBranding`.
Changing this display setting does not rename native package/bundle identifiers.
Colors follow the active public `WebAppearance`; bundled brand tokens provide
the cold-start fallback. Retry text contrast follows the actual primary color.

## Failure and retry behavior

Safe failure categories distinguish connection interruption, timeout, temporary
service failure, secure-connection failure and browser startup/process failure.
Native URLs, addresses, paths and raw engine descriptions never enter this UI.
Guidance suggests Wi-Fi/mobile data, airplane mode, an active data bundle,
another network, waiting for service recovery, or the appropriate secure/browser
checks. It does not claim to measure data balance or prove an internet outage.

The browser surface is offstage with its state retained during failure and
retry, excluded from focus/semantics. Recovery stays visible until a valid
document completes; duplicate retries are blocked. Failed documents are not
treated as usable by late start/finish callbacks. Retry loads the intended URL
through the same controller and persistent profile, including on Windows where
the engine can otherwise reload its internal error document.

Subresource errors, unrelated/stale document failures and deliberate WK/Windows
cancellations do not replace a usable application page. Android document 5xx
responses and Windows main-frame 5xx responses use service guidance; application
4xx responses stay web-owned. WK HTTP callbacks lack document identity and stay
web-owned; its actual navigation failures use the native recovery screen.

aborted requests, 503 responses and recovery to the original route/controller.
