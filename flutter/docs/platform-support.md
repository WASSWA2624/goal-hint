# Flutter shell platform support

Evidence checked **26 October 2026 (Africa/Kampala)** for [foundation plan 001](../dev-plan/001-foundation-and-platform-support.md). The candidate tables below preserve that foundation decision record. A generated runner, a documented engine feature, and a tested WebView are different levels of evidence. Plan 003 now implements browser adapters; see [the current integration guide](web-app-integration.md) and [execution tracker](../dev-tracker.md) for their actual checks. No offline cache is implemented by browser embedding.

## Toolchain baseline and evidence labels

The selected local SDK is **Flutter 3.44.6 stable**, framework revision `ee80f08bbf`, with **Dart 3.12.2**. The foundation execution records actual doctor, build, and run results in [the tracker](../dev-tracker.md). The Windows host has Visual Studio 2026/CMake and an Android SDK; its Android SDK path contains spaces and a stale `JAVA_HOME` requires a process-local JDK selection. These are host configuration findings, not evidence that Android or a plugin is unsupported.

The current online Flutter platform reference describes **Flutter 3.47**, which is newer than the selected local SDK. Its deployment ranges below are current documentation guidance, **not a claim about 3.44.6's exact minimum OS versions or local test coverage**. Preserve the generated project's actual target settings and verify the intersection of SDK, plugin, engine, architecture, and distribution requirements when selecting a plugin. [Flutter supported platforms](https://docs.flutter.dev/reference/supported-platforms).

- **Documented:** a primary source describes the capability for that engine/package.
- **Prototype required:** the actual selected plugin, OS, origin, and persistent profile have not demonstrated it in this app.
- **Unsupported by package:** the released package does not advertise that target.
- **Host unavailable/untested:** a required build host or device is absent; this does not mean the platform or plugin is unsupported.

## Integration strategy for plan 003

Use one small shell-facing contract for loading, navigation/lifecycle/error signals and supported capability reporting. Prefer `webview_flutter` for Android/iOS/macOS, with a separate WebView2-backed Windows adapter; compare the two Windows candidates before pinning a dependency and locking it. Do not introduce a large adapter abstraction or a native business/data layer during foundation generation.

Keep Linux as an explicit integration gap, with `webview_cef` as the first prototype and WebKitGTK as the alternative if the CEF footprint or native integration is unsuitable. A candidate that fails prototype acceptance must leave Linux marked unsupported **by the selected app integration**, while retaining the distinction that Flutter itself supports a Linux runner. Opening a separate system browser does not satisfy the embedded-shell requirement.

Plan 001 added no candidate dependency. Plan 003 pins the official system plugin for Android/iOS/macOS and a locally patched, directly imported Windows 0.6.0 adapter. The Windows patch is necessary because the stable plugin's network interception callback alone does not guard every navigation scheme. Its source, license, archive hash, and native guard tests are retained in [the upstream record](../packages/flutter_inappwebview_windows/UPSTREAM.md). See [integration behavior and evidence limits](web-app-integration.md). Platform support remains a requirement, not an accomplished five-platform release.

## Gates before offline claims

[Shared web plan 069](../../next-js/dev-plan/069-offline-shell-support.md) owns the eligible entry/assets/read cache and auth-safe update contract. Flutter [004](../dev-plan/004-persistent-offline-startup.md), [005](../dev-plan/005-reconnection-and-cache-updates.md) and [007](../dev-plan/007-platform-builds-and-release.md) must prove that contract in the installed apps.

For each chosen engine, record its exact version, OS/architecture, selected plugin/lockfile and origin. Then demonstrate navigation and web sign-in/logout; cookie/profile persistence across full process termination; service-worker registration or the documented minimal adapter alternative; permitted local asset delivery; and eventual online → terminate → offline cold start → reachable-server update. Include first-use offline, eviction/corruption, failed update, expired/revoked access and untrusted external navigation. Separate local file origins, development LAN origins and the hosted HTTPS origin instead of assuming shared cookies/storage.

Persistent browser storage alone does not implement offline startup. Do not cache private/no-store pages, subscriber responses, credentials or payment evidence, relax the web authorization rules, or queue account/financial writes to make a prototype pass. Retain the last validated public cache if an update fails, and preserve active input when applying a new version. These are later acceptance requirements; none is claimed complete by the foundation scaffold.
