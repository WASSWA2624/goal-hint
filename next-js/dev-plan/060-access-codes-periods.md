# 060 Access codes, periods and access resolution

**Feature:** 12-character access codes bound to the paying account, paid periods with queueing, device unlock with a cap, viewer access resolution, the owner code services and the one-tap `#code` link.

**Depends on:** [059-phone-sign-in.md](059-phone-sign-in.md).

**Source:** [App specification](../../app-write-up.md), sections 1 and 13 (version 1.9 paid access); [monetization plan](../../prompts/monetization.md), sections 3 (security model, code binding, device unlock, renewal, code format and storage, period), 5.3, 5.5 (access resolution), 5.8, 5.9 (fragments), 6 (account page), 8 (060) and 9.

## Prompt

Read `next-js/dev-plan/000-index.md`, the source sections and existing code before implementing this feature. Public reads are not gated yet (061); this prompt makes entitlement exist and resolvable.

- **Code format** (`src/domain/access-code.ts`): 12 Crockford base32 symbols (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), shown as `XXXX-XXXX-XXXX`; case-insensitive; spaces and dashes ignored; O→0, I/L→1. `formatCode`; `extractCode(text)` takes the first dashed `XXXX-XXXX-XXXX` group in pasted text, otherwise the input without spaces and dashes must be 12 symbols; `codeFromFragment(hash)` accepts only `#code=` plus a valid code. The code field uses `autocapitalize=characters`, `autocorrect=off`, `spellcheck=false`, `autoComplete=off` and `data-analytics-ignore`.
- **Code storage** (`src/server/members/access-codes.ts`): `generateCode()` (`crypto.randomInt(32)` × 12), `newSalt()` (16 random bytes per code), `hashCode(salt, code)` = SHA-256 of `goal-hint-access-code:v1:` + salt + code, `newReference()` (a random `C-XXXX`, independent of the code), `activate(code, account, now, termsVersion)`. No key is used, so rotating `GOAL_HINT_ANALYTICS_SECRET` cannot break codes.
- **Periods** (`src/domain/subscription-period.ts`, pure): `codeStatus(code, now)` in order `revoked`, `queued` (now < `startsAt`), `active` (now < `endsAt`), else `expired`; `chainPeriods`; `remainingDays`; EAT display. Access runs from payment confirmation to the expiry time (owner decision, OP-38). Activation happens in the transaction that creates the code (approval of a reported payment in 064, or the owner creating a manual or number-change code) and sets `activatedAt = now`, `termsVersion` from the submission when there is one, `startsAt = max(now, latest endsAt of the account's non-revoked codes)` and `endsAt = startsAt + (durationDays + extensionDays) × 24 h`. Code entry never starts or moves a period, and there is no unused state.
- **Code entry** (`POST /api/account/code`): one transaction with `SELECT … FOR UPDATE` on the account row, following plan 5.3 steps 1–6. Compare in constant time with the codes **of the session's account** only; a correct code works even while the IP throttle is locked. `active` or `queued` unlocks with the period unchanged. A line above Unlock reads "By unlocking you confirm you are 18+ and accept the Terms", with no checkbox, and a code without `termsVersion` (manual and number-change codes) records it now. `expired` or `revoked` gives a clear message ("This code's access ended on …") and no unlock. A session that was not unlocked gets a **new** token: insert a session with `codeEnteredAt` and `accessCodeId`, delete the old row, set the cookie and audit `device_unlocked`. Above the settings' max unlocked devices, clear the oldest unlock and audit `device_evicted`. Not found (a wrong code or another account's code): "Code not recognized. Codes work only on the number they were sent to." with a "Not your number? Sign out" link, and a wrong attempt counted for the IP (100 an hour). JS gets JSON naming the next path (the validated `return`, else `/en/account?status=code-accepted`) and does a full `location.replace`; no-JS gets a 303 there. A blocked account gets the generic refusal.
- **Phone plus code** (signed out): the sign-in route with a code looks up the account and never creates one. No account, or no matching code: the generic "Code not recognized", no session, a wrong attempt counted. A match creates the session and redeems in the same transaction.
- **Entitlement**, checked on every request in one SQL round trip (session primary key, (`accountId`,`endsAt`) index): a valid session; an account not blocked or erased; `codeEnteredAt` set; a non-revoked code of the account with `startsAt ≤ now < endsAt`. Expiry needs no job.
- **Viewer access** (`src/server/members/viewer-access.ts`): `resolveViewerAccess()` for pages (React `cache()`, reads `cookies()`) and `viewerAccessFromRequest(request)` for handlers, both returning `{ tier: "full" | "free", signedIn, mode }` in the order of plan 5.5: mode `off` → full; a valid owner session, checked only when the owner cookie is present with `verify(token, { touch: false })` → full; an entitled member session → full; mode `test` and no member session → full; anything else, including any error → free.
- **Owner services** (UI in 064–065), each under the account row lock and audited:
  - **Revoke** (reason): later queued periods move up; sessions that entered the code lose their unlock.
  - **Extend** 1–60 days: `extensionDays += N`; this and later periods shift.
  - **Reissue** (lost code, same account only): revoke the old code with `replacedById` = new; create one with the same snapshot and `extensionDays` and `paymentSubmissionId = NULL`; copy `activatedAt`, `startsAt` and `endsAt`; move sessions that entered the old code to the new one.
  - **Reverse payment** (approved only; `network-reversal` or `wrong-account`): the submission becomes `reversed`; revoke the live code at the end of its chain (followed through `replacedById`); `approvedTxnKey` stays.
  - **Manual code**: number (creates the account if missing), plan or a day count (1–366), amount received (0 allowed), required note; it binds to that number's account, and its period starts at creation, when the payment is confirmed. Network and transaction ID are optional and then require a plan. With an ID, one transaction records an approved `owner` submission (no image; `amountReceivedUgx` on the submission) and creates the code through the same approval function that 064's form approval uses, so the unique `approvedTxnKey` applies to both.
  - **Change number** (`newPhone`, `verifiedBy` = `old-number` or `payment-details`), one transaction: lock both accounts in id order; revoke every active and queued code of the old account (reason `number-change`, `replacedById` = new); compute the remaining time (active remainder rounded up to whole days, plus the full days of queued codes, 1–366); create one `number-change` code on the new number's account, creating it if missing, with its period starting now or when that account's current period ends; audit each revoke and the new code with `verifiedBy`. No code path ever rewrites `accountId` on a code, submission or session.
  - **Free trial** (plan 5.10): for an account with no code and a trial request, create one `trial` code of `trialDays` days with amount 0, starting now; **Dismiss** sets `trialDismissedAt`. Both are refused once the account has any code.
- **`#code` link** on the account route's root client component, in every state including mode off and refusals: read `location.hash` with `codeFromFragment` on load and on `hashchange`, and prefill. Clear it with `setTimeout(() => history.replaceState(null, "", pathname + search), 0)`. Never copy `history.state` as `src/components/analytics/tracker.ts:76` does: in Next 16.4 that skips the router sync (`node_modules/next/dist/client/components/app-router.js:302-310`), so a later `router.refresh()` would write `#code=` back. Apply the same `null` fix to `tracker.ts:76` for `#gh_attr=`. Never submit on its own. Signed out, show the phone field (`256` prefilled, focused, cursor at the end) above the code; signed in, focus Unlock. In in-app browsers, add a **Copy code** button when a code was prefilled. On goalhint.com the code never enters a query string, title, analytics label or server log.
- **Proxy:** `createDiscoveryProxy` (`src/server/seo/proxy.ts:36-43`) still strips click IDs on `/en/account` and `/en/subscribe` but sets no `#gh_attr=` fragment, so the browser keeps `#code=`.
- **Account states:** code accepted ("Unlocked." and a primary "See today's picks" to `/en`; with a `return` path the page goes straight there); active on this device ("Access until Sun 25 Oct, 21:00 EAT", "{n} days left", queued periods, a primary **Renew** button to Get access, code box, devices with last-used dates and Sign out others, Sign out); ended (unlocked sessions only: "Your access ended on …", Renew, code box, Sign out others). Payment status shows only to the submitting session and to unlocked sessions of the account; a number-only session sees no status, periods or history.
- **Route guards:** extend `tests/admin-routes.test.mjs`: `POST /api/account/code` accepts a session that is not unlocked, refuses cross-site requests (403) and mode `off`, and gives a blocked account the generic refusal.

**Files.** New: `src/domain/access-code.ts`, `src/domain/subscription-period.ts`, `src/server/members/access-codes.ts`, `src/server/members/viewer-access.ts`, `src/app/api/account/code/route.ts`. ## Acceptance checks

Run `npm run test:members` and `npm run test:seo`.

- Periods: a code's period starts when it is created, never at unlock; a Daily code confirmed at 14:30 EAT ends at 14:30 EAT the next day; two codes created concurrently for one account chain without overlap; a queued period starts at the previous end; a code entered late unlocks only the remaining time; unlock records `termsVersion` on a code without one.
- Unlock: a device unlocked once stays entitled across renewals; the cap evicts the oldest unlock; unlock issues a new token; a correct code works while the IP bucket is locked; expiry flips without a job.
- Reissue: the new code has `paymentSubmissionId = NULL` and takes over the sessions, and the old code's `replacedById` points to it.
- Reverse: it revokes the live code at the end of the chain, including a number-change code.
- Change number: 3 days 5 h active plus a queued 7-day code become one 11-day code. Old-account sessions lose entitlement, and no code is created on the old account.
- Free trial: an account with any code is refused a trial code, and a trial code lasts `trialDays × 24 h` from creation.
- Binding: another account's code is "not recognized", whether signed in or through phone plus code. Phone plus code then creates no account or session.
- A number-only session is never entitled and sees no status; test mode gates only member sessions; `resolveViewerAccess` and `viewerAccessFromRequest` agree against real sessions and codes.
- `/en/account?fbclid=x` gets a 308 whose `Location` has no fragment; the code input renders `autocomplete="off"`.
- Unit: `extractCode` on the whole message (including the link line), `codeFromFragment` (only `#code=` plus a valid code), salted hashing, `chainPeriods`, revoke, extend, reissue, `remainingDays` rounding and EAT display.
- Manual: the `#code` link prefills, never auto-submits, and works signed out with only the phone typed. After Unlock (or a `router.refresh()`), `location.hash` is empty and `history.state.__PRIVATE_NEXTJS_INTERNALS_TREE` still exists. Account states work at 375 px.
