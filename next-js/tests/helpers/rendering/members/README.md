# Synthetic account acceptance app

Run `python scripts/verify-member-rendering.py --serve` from the Next.js app directory. The script builds the fixture, checks its initial HTML and synthetic API responses, and prints its local browser URL. No database, account creation or message provider is used.

Repeat checks against an already built fixture with `--fixture .tmp/members-<id>`. Omit that option after application changes so the fixture uses current sources.

`verifyAuthenticationForms` from `scripts/verify-authentication-forms.mjs` accepts a Playwright page and `{ origin, widths, captureDirectory }`. Run it in isolated light/dark and fine/coarse-pointer contexts. It checks bounded form widths, grouped link actions, phone outlines, control geometry, synthetic recovery and country-picker behavior. It verifies the fixture metadata before submitting any request. Use `?state=support&view=forgot` to inspect the synthetic multi-contact support layout.

`verifyAuthenticationJourneys` from `scripts/verify-authentication-journeys.mjs` exercises signup confirmation and cancellation, duplicate-number feedback, immediate signup with and without a trial, legacy verification, password recovery, phone and password changes, member and admin login, logout, browser Back, cross-tab identity refresh, and recoverable transport errors. `/en/subscribe` uses the production route with the same scripted services. Guests and restricted sessions must reach the matching Account form. The session-unavailable scenarios verify the unavailable state for failed reads.

- `/en/account?state=unverified&view=verify` opens code entry for a legacy restricted session. Use a previously issued code or choose **Forgot password**.
- `/en/account?view=forgot` opens the recovery confirmation dialog. `state=support` shows all configured contact actions after submission.
- `/en/account?view=reset-code` opens the form for a previously issued recovery code.
- `/en/account/reset-password` accepts a synthetic fragment containing 43 lowercase `p` characters. Successful redemption returns to Login and marks the link used for that fixture browser.
- `/en/account?view=register&return=%2Fen%2Fmatches` exercises immediate signup and the final `/en/matches` home destination.
- **Start automatic trial signup** in the fixture controls resets the synthetic session and opens `/en/account?view=register&scenario=automatic-trial`. Enter `256700000101` and a password of at least 8 characters. Confirm the phone number to open `/en/matches` with the two-day trial already active.
- `/en/account?state=password-reset&view=new-password` shows the reset-password form directly.
- `/en/phone-fields` exercises shared phone fields and native FormData independently of authentication.
- Existing `state` values, refresh and browser-history probes remain available.

Subscription navigation uses the production private `/api/account/session` handler. Set `goal-hint-member` to the authenticated synthetic token (`a` repeated 43 times) and `member-fixture-subscription` to `free`, `active`, `manual`, `trial`, `pending`, `pending-renewal`, `expired`, `off`, or `off-active`. Without the member token, the same sales setting exercises a guest; the administrator token is `d` repeated 43 times. Direct HTTP checks may send `X-Subscription-Fixture-State` instead of the scenario cookie.

The additional `registration-trial` subscription scenario has its own deterministic two-day period beginning at the current UTC midnight. The `automatic-trial` registration response returns `active: true` and an authenticated synthetic signup cookie. A regular registration without an offer receives the same authenticated cookie, with the `registration-no-trial` subscription scenario. The production session handler rejects the separate legacy pending-verification cookie until the member verifies an existing code or recovers the account. Existing `trial` and other active scenarios retain their original seven-day expiry.

Inspect `/en` for the public header, `/en/matches` for the compact feed header, and `/en/matches/synthetic/preview` for the actual match-detail header. `/en/account` follows the scenario cookie for signed-in members; its `state` query also accepts the subscription scenarios. Active/manual/trial scenarios share a deterministic expiry within each fixture process. Pending renewals preserve that expiry, while `off-active` retains access with purchases closed. No fixture payment approves access automatically.

The **Fixture API outcome** selector controls subsequent calls without reloading or clearing the current form. It supports `success`, `send-failed`, `rate-limited`, `invalid-code`, `unavailable`, and `automatic-trial`. Set the same value using `?scenario=send-failed` when opening a page. The selection is stored in a fixture cookie and survives full-page navigation. Direct HTTP checks can override it with the `X-Member-Fixture-Scenario` header.

Use **Forgot password** from Login to check that the dialog starts with the entered number, remains open after a request, and displays the configured contact URIs. The `existing-request` scenario exercises the duplicate acknowledgement. `send-failed` exercises the unavailable response. Choose **Use a previously received code** to try the transition flow. The valid synthetic code is `123456`. The fixture’s paste buttons dispatch synthetic paste events without accessing the system clipboard. The valid sample trims outer whitespace. The invalid sample contains message text around the digits and produces an inline error. **Back to login** from a pending verification submits sign-out and clears the synthetic pending cookie.

Registration, login and legacy verification use the production auth HTTP adapter with scripted services and finish at the synthetic `/en/matches` home page. A phone change with the current password enters restricted **Forgot password** recovery. A valid previously issued code opens the legacy reset-only page and choosing a new password restores the normal session. The new link flow returns to Login after the successful save. Payment, access and referral updates remain in the Account inbox.

The same login form accepts synthetic administrator `256700000991` with password `Synthetic admin password`, then opens `/admin`. The minimal `/admin` and `/analytics` pages exercise the production authorization gate and contain a logout button. Ordinary member login still opens `/en/matches`; `denied`, `missing`, `blocked`, `pending-verification` and `password-reset` API scenarios cover refusals and restricted sessions. Legacy `/api/admin/login` and `/api/analytics/login` handlers are the production redirect adapters. The acceptance script also checks legacy-owner-only and mixed ordinary/restricted/invalid member cookies, credential-version expiry, account/session role consistency and clearing both cookies on logout.

On `/en/phone-fields`, inspect the form before entering anything: required account phone and optional admin search must both serialize as empty strings. The required visible input must block submission until valid; empty optional search must remain valid. Enter a local national number and inspect again: only the hidden canonical field name should be serialized, with the full country code and no `+`. Search the country picker by country name, ISO code and calling code. The controlled international field starts in Kenya; **Set controlled UK phone**, **Clear controlled phone**, and **Focus controlled phone ref** check external state changes and forwarded input focus. Type a partial number, then use **Paste synthetic full UK phone** to confirm a full paste replaces the old country/prefix. The invalid paste button contains message text and must be refused. These paste probes use synthetic browser events and do not read or write the system clipboard.
