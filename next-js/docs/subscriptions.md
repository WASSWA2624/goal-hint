# Manual subscriptions and public access

Members register with a phone number and password, then verify their registered number through SMS or WhatsApp in supported countries. Paid access starts only after an authenticated administrator approves a payment request; the member does not enter an activation code. See [member-authentication.md](member-authentication.md) for verification, recovery, and administrator credentials.

## Public and subscriber views

Every visitor, signed in or not, can see match probabilities, fixtures, and scores. Probability filters and sorting are public. For upcoming/live matches the server removes prediction selections, market details, odds, and prediction analysis/history before returning HTML or API data. Clicking protected content leads guests to registration and signed-in members to Subscribe.

Once a match reaches a played final status (regulation, extra time, or penalties), everyone can view its historical predictions, odds, analysis, revisions, and results. Merely reaching its kickoff time does not unlock it. Postponed, canceled, abandoned, awarded, and unknown-status fixtures remain gated until a played final status exists. Active picks/odds filter requests remain protected so filters cannot reveal hidden selections.

Admin sessions and members with a current approved subscription get the full view. Raw premium caches stay on the server; final responses are private/no-store and vary on Cookie. Subscription sales mode `off` closes purchases and requests without granting public premium access. Existing approved periods still expire normally. New registrations receive one automatic free-trial access period using Admin Settings → Free trial on registration (days). A value of 0 disables new trials. The period starts at registration; ordinary phone verification is still required before the session can use premium access. No trial request or administrator approval is involved.

## Packages and payment

The standard package migration adds missing duration offers: Daily (1 day, UGX 1,000), Weekly (7 days, UGX 5,000), and Monthly (30 days, UGX 20,000). Existing offers/prices are preserved; admins can edit prices and availability. Every package unlocks the same features. Days are 24-hour periods from approval, and renewals extend the account's existing unexpired period.

1. Log in and choose an available daily, weekly, or monthly package. The server supplies its amount; the client cannot choose a cheaper amount.
2. Choose MTN Mobile Money or Airtel Money. Check the displayed receiving number and registered name, then pay using the chosen network.
3. Enter the required transaction ID from the payment SMS and confirm the visible, required **Paid from** number, initially filled with the account number. Change it if you paid from another phone. The **Screenshot (optional)** upload and photo controls are always visible. If an image is attached, the browser prepares a JPEG and the server checks image type, dimensions, and size; duplicate images are flagged for review. Submitting without an image still counts toward request limits. No external payment gateway or message sender is called during submission.
4. Review the details, confirm that payment was made, accept the current Terms when needed, and submit proof. Pending, rejected and reversed reports show the reference, plan and amount, followed by **Call** and **WhatsApp** buttons for the configured contacts. Pending reports also show **Sent** directly; **More details** appears only when a review-time estimate is configured. Rejected and reversed reports keep **Sent** under **More details**, with the rejection reason or reversal message visible. **Update payment details** opens the correction form for pending or rejected reports. **Submit another payment** opens a new form after reversal. The form omits the status panel; **Back to payment status** closes it without losing the draft. The administrator manually verifies the receiving-wallet transaction and account ownership under Payments, then approves or rejects it.
5. Approval creates a single account-bound access period, marks the request approved, and unlocks the account's signed-in device. Existing pages refresh pending status. Subsequent password logins inherit approved access while the period remains valid and sign out the previous device. A rejected report never unlocks access.

Admin → Payments lists the payer number, reported amount and transaction ID. The review form starts with the reported ID and amount, which remain editable, and displays any attached screenshot. After checking the receiving wallet, the administrator confirms with **Approve payment**. Rejection is a secondary action; reversal is available only for approved payments.

Only one device can be signed in to an account at a time. The login form warns users before they submit. Separate browsers and in-app browsers count as separate devices. Changing devices preserves the account's subscription and remaining time. Legacy subscription device-limit settings remain for compatibility, but cannot permit simultaneous logins under the stricter authentication policy.

After a payment approval or rejection is committed, Goal Hint attempts one YoolaSMS notification to the registered account number, including payments recorded manually with a transaction ID. It never sends to a separate payer number. Payment, credit and renewal messages use a minimal account-update notice directing the member to sign in or contact the administrator. Financial details, payment references and decisions, package names, expiry times and review reasons stay in authenticated account views.

The admin success notice reports that the account-update SMS is queued. The decision and its minimal delivery intent commit atomically; the private worker later records provider acceptance, unconfirmed failure, unsupported/missing destination, cancellation or interruption. Missing credentials or delivery failure do not reverse the payment decision or access grant. Refused or repeated decisions queue no further message. Queued work survives process interruption; a dispatch claim interrupted for at least one minute becomes `uncertain` for operator reconciliation and is never automatically resent. Overview shows notices requiring attention; an explicit owner **Send again** queues a fresh fenced attempt and warns of possible duplicates, while **Dismiss** removes a closed notice. Both actions are audited. Yoola acceptance does not confirm handset receipt. The three-message verification-code allowance does not apply to these payment decision notifications. See the [messaging runbook](yoola-messaging.md#payment-decision-notifications) for migration, grants and worker supervision.

Submitted requests retain their package name, price, and duration, even if an admin later edits the offer. Duplicate transaction/image checks and locked account/payment decisions protect against repeated approval. Receipts are evidence for manual review, not automatic payment confirmation. Reversal and blocking revoke access without deleting the payment/audit history.

Payment references display as `P1234` without a separator. Transaction IDs are normalized to uppercase without spaces or hyphens; duplicate detection still uses the same canonical key. Historical references with the `P-` prefix remain searchable.

The user can call the administrator if approval is delayed. Optional support-chat links are user-initiated only; no WhatsApp message or SMS activates the account.

## Environment configuration

Receiving wallets and support contacts are private server configuration:

- `GOAL_HINT_MTN_MOMO_NUMBER`, `GOAL_HINT_MTN_MOMO_NAME`
- `GOAL_HINT_AIRTEL_MONEY_NUMBER`, `GOAL_HINT_AIRTEL_MONEY_NAME`
- `GOAL_HINT_CUSTOMER_SUPPORT_NUMBER`, `GOAL_HINT_CUSTOMER_SUPPORT_WHATSAPP_NUMBER`
- Optional verified menu shortcuts: `GOAL_HINT_MTN_MOMO_MENU_SHORTCUT`, `GOAL_HINT_AIRTEL_MONEY_MENU_SHORTCUT`
- Payment decision SMS uses `YOOLA_SMS_API_KEY` and optional `YOOLA_SMS_SENDER` in development and production; see [yoola-messaging.md](yoola-messaging.md).

Use country-code numbers. Both number and registered name are required for a wallet to appear. Support numbers are separate and never inferred from wallets or the admin allowlist. Admin Settings shows environment-managed identities read-only. Restart after changing environment values. Never seed or commit real credentials or receiving numbers.

## Saved slip history

A subscriber can save a generated slip for tracking. The save endpoint rebuilds selections on the server from validated criteria and refuses invented/client-supplied odds, expired sessions, reset-only sessions, non-subscribers, and already-started fixtures. Saving a slip does not place a bet with a bookmaker.

Completed slips are public on the Slips page when every original leg has ended or its recorded original cycle has been formally voided. Canceled, abandoned and awarded forecasts follow the existing void rules. Original saved predictions, probabilities, odds, and verified regulation scores remain visible; wins/losses use the existing market-settlement rules. A pending correction stays visible without reviving an older win, and a replacement cycle never grades the original leg. Missing verified scores display a pending outcome. An early losing leg does not reveal other still-active selections. Legacy saves without cycle references remain explicitly unbound. Owner account IDs, phone numbers, and credentials are never included. Erasing an account removes its saved slips.

No historical slips are invented or backfilled. History accumulates from explicitly saved slips after this feature is deployed.

## Account credit

Credit is a plan-only, non-refundable balance on an account. It comes only from payments the owner approves: a top-up report (**Add credit** on Get access, UGX 1,000–500,000), or what a plan payment received above its plan's price (up to UGX 500,000). It is spent without approval: **Pay from credit** on Get access buys the chosen plan at once, and auto-renewal (turned on per plan on Account, which accepts the current terms; renewed periods record that version) renews the plan from credit within an hour of the access period ending. Turning auto-renewal off works even while sales are closed (the credit endpoint refuses only buying and turning it on then). A renewal the owner revokes is not bought again for the same period end, and the account then no longer shows "Renews from credit". Renewal runs from the members worker (`npm run members:renew`, every cron slot), the live runner and owner page loads, and on the member's own visit; each renewal is keyed by the period end it renews, so none of these can charge twice. The background job renews only lapses under a day old; after a longer outage the member's next visit renews and the new period starts then. A renewal atomically queues the same minimal account-update SMS; Account shows the expiry and remaining credit. Apply the additive `20261025230000_payment_notification_outbox` migration and grants before deploying, and supervise the [private SMS worker](yoola-messaging.md#payment-decision-notifications).

`WalletEntry` is the ledger: one row per change, with the amount, the resulting balance and the payment or access period it names, under the account's row lock. `MemberAccount.creditUgx` caches the newest balance. The application role can only SELECT and INSERT ledger rows; triggers refuse updates and deletes. Reversing a payment whose credit was already spent takes the balance below zero, which blocks spending until a top-up clears it. A number change moves credit and auto-renewal with the access (it is refused while a top-up waits for review, since reports never change account), and records an `AccountMove` row (from, to, the old account's newest ledger entry number, time; ordered by an auto-increment sequence, exact because moves touching one account serialize on its lock). A later reversal's debt goes where that payment's credit went: from its ledger entry, along the first move recorded at or after it and then each later move out of the account it reached, to the account holding it now (paired transfer rows; the reversal row itself stays on the paying account). Credit an old account received after its move is taken back there. `AccountMove` is append-only (SELECT and INSERT for the application role; triggers refuse updates and deletes) and its foreign keys RESTRICT, so an account in a number change can be erased but not permanently deleted: Delete account refuses with a message to erase instead. An erased account records no reversal debt, since erasure already forfeited its credit. Erasing personal data forfeits a positive balance (a recorded correction); permanent deletion removes the ledger with the account. Admin → Subscribers → Credit shows the balance and history, corrects credit with a reason, and can turn auto-renewal off. The Overview shows credit held by members, which is owed in plans and is already counted in revenue from the payments that added it.

Screenshots are private JPEG responses behind the shared admin guard. Pending screenshots do not expire automatically; decided screenshots follow configured retention. The existing members purge removes expired sessions and rate-limit buckets. Account erasure clears credentials, private payer fields, proofs, verification rows, and saved slips while retaining required financial/audit attribution.

Admin → Subscribers places the searchable directory beside the selected account on desktop. On smaller screens, **Find account** opens the directory. The account toolbar opens one task at a time: grant access, change number, reset password, block/unblock, sign out devices or delete. Overview, Access, Payments and Devices tabs keep notes and history compact. **Add subscriber** uses the existing manual access grant for a new or existing number; it does not set a password. Optional transaction fields appear under Payment details. Access periods support inline extension and confirmed revocation.

On Admin → Subscribers, **Delete account → Permanently delete account** requires explicit confirmation and removes the account and all related credentials, sessions, verifications, saved slips, payment records/screenshots, access periods and related audit data in one transaction. **Erase personal data instead** retains accounting history. Previously erased accounts can also be deleted. Other accounts and shared subscription plans remain available; deletion changes payment and subscriber totals. Apply the additional DELETE grants on `PaymentSubmission`, `AccessCode` and `OwnerAuditEvent` from `deploy/manual-account-grants.sql` before deploying this flow. No schema migration is required. Backups retain their existing lifecycle; reapply account deletions before promoting a restored backup.

Run `npm run db:generate`, `npm run db:validate`, `npm run lint`, `npm run typecheck`, relevant member/payment/paywall tests, and the production build. Database integration tests require an isolated genuine MySQL installation or an explicitly approved isolated test target; unavailable MySQL means skipped integration coverage, not a successful migration.
