# Community and payment-review alerts

Source handover, 3 November 2026. Nothing in this change deploys the application, changes receiving wallets, approves a real receipt, enables outbound delivery or publishes an installer.

## Behaviour and safeguards

The existing desktop and phone **More** menus gain Community when an enabled destination is configured. The existing public modal shows WhatsApp Channel, Telegram Channel and WhatsApp Group with platform/group icons. All account states can open them. Admin **Settings → Support → Community** stores validated HTTPS links in the existing settings row. Empty/disabled destinations stay hidden; active clients refresh configuration within roughly 30 seconds. Native hosts reuse their existing external-link policy, keeping external documents outside the authenticated WebView. Joining does not award referral days. Sharing remains manual through the existing slip exporter.

Checkout, reservations, wallet/referral arithmetic, receipt ownership, verification and final approval retain their existing rules. Identical repeated receipt attachments now leave the revision/evidence history unchanged. An outstanding review retains one event through ordinary edits. An administrator's correction/shortfall decision resolves it; a meaningful resubmission creates the next event. Internal-only confirmed purchases do not create external review alerts.

Existing customer messaging was traced separately: legacy receipt approval/credit and credit-funded renewal enqueue their configured account-message events; current checkout uses its private inbox and entitlement refresh. Yoola delivery still depends on templates, consent, credentials and its existing worker. The owner's reported phone confirmation could not be correlated with a live event/provider log in this task. No duplicate activation message or paid fallback was introduced.

`PaymentReviewEvent` commits inside the existing receipt/account transaction. `PaymentAlertEndpoint` belongs to an authenticated `MemberSession`; deleting/evicting a session cascades its endpoints and deliveries. Registration and dispatch check current administrator allowlisting, credential version, account state and session expiry. No public topic, device fingerprint or customer messaging fallback is used.

`PaymentAlertDelivery` leases each event/endpoint pair, retries with bounded backoff (five attempts), records provider acceptance separately from display/open observations, and removes invalid endpoints. Resolution uses the same event to request removal of obsolete OS notifications, with its own bounded retries. Clients also reconcile on resume. Endpoint rotation, muted devices and role/session revocation are rechecked before dispatch. A provider failure cannot roll back payment accounting. An alert already accepted by a provider can race with logout or a decision; opening always authenticates and reads the current server state.

Notification content is generic; only opaque identifiers and event time cross transports. Tapping enters `/payment-review/<uuid>`, preserves the validated `/admin/payments?paymentId=<uuid>` destination through sign-in and uses the existing review route. Viewing, dismissing or opening never approves. Resolved reports display their current state. Evidence and approvals require connectivity; the existing offline screen is a public fallback, not payment access.

App closure is not logout. Denial, muted channels, DND, offline devices and force-stop restrictions remain authoritative. Android force-stop requires reopening the app; this implementation does not use alarms/calls or attempt to bypass OS limits. Separate browser profiles and a native installation are independent endpoints; use the device mute control for redundant alerts.

The original two-note chime is generated by `scripts/generate-payment-review-sound.py`: approximately **0.85 seconds**, **37,528 bytes**, mono 22,050 Hz PCM WAV. No third-party recording or copied messaging-app sound is used. The web master is `public/sounds/payment-review-v1.wav`; identical required copies are the Flutter Windows asset and Android `res/raw/payment_review_v1.wav`. Web responses are versioned/cacheable; private responses never enter the offline asset cache. Windows custom asset audio requires compatible packaging; unpackaged/debug builds use the plugin's normal system-sound fallback.

Default browser foreground playback is one chime; the existing settings mechanism permits **1–3** repeats, with a separate **650 ms** gap after each approximately 850 ms sound. Resolution, opening and session end stop repeats; old catch-up events stay quiet. Background/native OS notifications use one sound subject to system settings. There is no guarantee that a human heard it. SDK/OS display calls and provider acceptance are not proof of delivery timing.

## Owner setup and rollout

1. Review/back up, then apply **`20261103170000_community_payment_alerts`** using the existing migration role/workflow. MySQL uses the Prisma migration; MariaDB uses the matching overlay and checksum. Apply `docs/deployment/payment-alert-grants.sql` with the actual existing database/application principal. This migration has been applied only to isolated test databases in this task. No receipt/ledger/access data is deleted or rewritten.
2. Enter actual community URLs in Settings. No live/dummy destinations are configured by this change. Native apps need no rebuild for later URL changes.
3. For browsers, set private server environment values `GOAL_HINT_PUSH_SUBJECT` (valid VAPID mailto/HTTPS subject), `GOAL_HINT_PUSH_PUBLIC_KEY`, `GOAL_HINT_PUSH_PRIVATE_KEY`. Generate and retain a VAPID key pair securely; only the public key is returned to administrators. Serve the root worker over HTTPS with same-origin authenticated APIs. Allowed subscription services are FCM, Mozilla, Apple and Edge's `*.notify.windows.com`; arbitrary server-side endpoint URLs are refused.
4. For Android, configure the correct Firebase Android application for the existing `com.goalhint.goal_hint` identity. Build with public `GOAL_HINT_FIREBASE_API_KEY`, `GOAL_HINT_FIREBASE_APP_ID`, `GOAL_HINT_FIREBASE_SENDER_ID`, `GOAL_HINT_FIREBASE_PROJECT_ID` Dart defines. Gradle maps the same four values to Android string resources so Firebase can initialise before Dart on a cold background start; partial configuration fails the build, and omitting all four leaves native push unavailable. This uses Firebase's documented resource configuration without adding another configuration file/plugin. Keep the server service-account file outside the repository, point `GOOGLE_APPLICATION_CREDENTIALS` at it and set `GOAL_HINT_FCM_ENABLED=true` only for an approved configured server. Server identity/project and native app must match; grant only the required messaging permission. No private server credentials are embedded in web/native source.
5. Supervise `npm run payments:alerts -- watch` on the approved host, or invoke bounded `npm run payments:alerts -- run`. Watch checks every **5 seconds**; each batch is bounded. A one-minute/slow cron is not immediate delivery. Inspect actual host process/cadence limits and any operational costs before enabling; no paid provider or recurring service was purchased or added. The member SMS outbox remains a separate worker with its existing semantics.
6. Release coordinated web/worker/native updates after approval. **Settings → Payments → Payment alerts** defaults outbound delivery off. On each reviewer device choose Enable alerts; choose foreground sound separately in a browser. Test alert queues a real transport event without a payment/access grant. Status distinguishes queued/provider-accepted/display/open observations; an unconfigured endpoint or local sound is not a background-push pass. Older native hosts keep in-app behaviour and show an update requirement for native alerts.

### Windows approval gate

The existing Windows distribution is an unpackaged shell. Closed-process push requires a qualified WNS/Windows App SDK identity, registration, packaging and activation arrangement. The proposed next release work is a signed MSIX identity plus the matching Windows push registration/activation adapter and private server credentials, subject to the actual deployment requirements. This changes distribution and requires **owner approval before implementation/publication** under the implementation prompt. No daemon, startup task, hidden background service, speculative WNS endpoint or new distribution identity was installed. Running-host local alerts are independent of that approval.

### Rollback

Disable outbound Payment alerts and stop its worker first. Existing inbox/queue/manual approval keep working. Mute endpoints and reconcile notifications on client resume; already accepted provider messages cannot be recalled with certainty. Keep the additive tables/columns when rolling back application binaries. Do not drop receipts, ledger entries, audit history or access grants. Disable/hide community destinations through Settings independently. Retain the prior web/native release until the replacement is qualified.
