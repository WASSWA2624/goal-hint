# Payment checkout and reconciliation

`20261101120000_payment_checkout` adds the subscription and wallet top-up checkout. The customer flow now uses Package, Pay, Details and Review. Package prices and durations are unchanged. Existing access, referral periods, wallet history and payment references remain intact. New qualifying referred registrations earn one redeemable day; existing rewards are not awarded again or converted into money.

The customer explicitly confirms internal spending. External requests reserve wallet funds and referral days for 48 hours. All spend paths exclude reservations. Expiration, cancellation and rejection release them. Expired funding requires customer confirmation before approval, even when a receipt has already been verified.

The browser keeps its draft, step, idempotency key, message, corrections and accepted screenshot in account-scoped IndexedDB. A lost response can safely retry the same request. External receipts require a transaction message or screenshot; providing one marks the other optional. Both support pasting. Screenshots use bounded JPEG preparation and local OCR. Unreadable or incomplete screenshots prompt a retry/message choice; readable discrepancies use advisory warnings with Continue for admin review. Transaction ID and reported amount use persistent floating labels; amounts display thousands separators and the payer field groups digits by country while retaining canonical values. Raw evidence remains private and separate from receipt identity. Revisions of submitted evidence remain in private history. Browser-storage failures use the checkout dialog.

Details contains evidence and editable transaction fields. Review contains the funding breakdown, reported details, screenshot/message preview, terms checkbox and Submit. Wallet-only and referral-only purchases skip the evidence stage. Changing details clears consent. Payment date/time has no customer input: extraction supplies it when available. If absent, the existing non-null accounting field holds the submission timestamp, marked `paymentDateSource: submission`; admin review displays "Payment date not read from evidence" and requires the actual receipt date separately. No migration is needed.

Provider branding and receiving numbers are checked separately against the selected provider and configured destination. Known receiving numbers can be detected without a label; a sender's number does not count as the recipient. Provider/recipient differences, unknown providers, entered-field differences and disagreements between message/screenshot IDs, amounts, providers and recipients are advisory. ID comparisons use the same normalized identity as the receipt ledger; a differing character warrants a warning even when it could be an OCR slip. Checks run after extraction or a method change and before Review/Submit. Review details and Change method preserve evidence, while Continue for admin review explicitly acknowledges the current comparison. Changes to the compared details invalidate that acknowledgement; reloads require it again.

The Paste button and direct clipboard paste share readability validation before inserting a message or extracting fields. A complete readable transaction ID and amount are required. Invalid or oversized clipboard text leaves the current message and fields unchanged; readable method/source discrepancies remain available behind their warning. Clear appears to the left of Paste only while the field contains text, clears the message in one action and returns focus to it. Extracted details and an accepted screenshot remain available; an external request still needs a message or screenshot.

The server recomputes and stores warnings from the received evidence, ignoring client-supplied warning metadata. Warning-bearing reports require explicit customer acknowledgement and remain pending. Admin review lists the selected method and every discrepancy. An admin records findings against a server-generated evidence fingerprint; corrected evidence invalidates prior findings. Allocation requires both this review and actual receipt verification. A warning acknowledgement never verifies money, changes receipt identity or bypasses duplicate/ownership checks. If the transfer belongs to a different provider or receiving account, request correction instead of allocating it under the selected provider. Existing JSON evidence/history and audit records support this without a schema migration.

Each transaction accepts one screenshot. Source-byte and prepared-image SHA-256 checks block repeated copies within the draft, including after refresh. Pasting multiple images opens a chooser and collapses identical copies. A different image requires Replace screenshot or Keep current; the original stays until the replacement passes its checks. Removing the screenshot clears its validation metadata. Older saved images must be rechecked before submission. Screenshot OCR never overwrites a pasted transaction message or substitutes its text as message evidence.

Image hashes detect identical copies, not all crops or edits. OCR may misread characters, so customers must check extracted IDs and the admin must verify the actual incoming transfer. The provider and normalized transaction ID remain the payment identity.

An authenticated, rate-limited preflight checks the provider/normalized transaction ID before accepting screenshots and again on submission, including manual ID corrections. It returns a customer's own request reference only to that customer. Image-history checks are limited to that customer's records; image matching is advisory and never determines ownership. Already-reported payments can enter the existing disputed-ownership review route, while same-customer retries use the original request. Final allocation still depends on database uniqueness and verified incoming funds. Checkout dialogs ignore backdrop clicks and Escape, and close through their visible buttons.

The compact interface keeps progress numbers and labels inline, omits duplicate headings and step-count text, and pairs the four methods in two rows. The pay step uses one brief amount/duration sentence above the provider number and inline copy icon. Additional wallet funding stays visible when used. The payer's floating "Number used to pay" label sits above the editable digits, beside the country selector. Tapping a screenshot in Details or Review opens a large private preview in the same tab, with button-only dismissal. Removing an image preserves extracted fields; Next remains available and explains in a dialog that a screenshot or message is still required. Screenshot extraction preserves an already-entered transaction message.

Wallet balance is a selectable contribution whenever any spendable credit is available. Customers can use part of it and choose MTN or Airtel for the remainder; provider changes preserve partial contributions. Max uses the permitted balance, and fully funded wallet purchases omit external proof. Confirmation uses Submit. Checkout errors, verification information, and shortfall/excess acknowledgements use the shared modal dialog; a reported shortfall can still be submitted for later top-up.

Referral days can be selected alongside any paid funding source. Seven purchased days plus seven referral days grants fourteen days while charging the original package price. Selecting referral days without a paid funding source retains referral-only redemption. The synthetic browser fixture includes seven referral days for this example.

`PaymentReceipt` uniquely identifies `(provider, normalized transaction ID)`. Verification records the reviewer, actual amount, recipient, receipt time and available sender number. Approval separately allocates receipts, debits reservations, grants access and credits excess in one transaction. Each receipt and request can be allocated once. Genuine excess is credited rather than refused because it exceeds the package price. Integer wallet balances support up to UGX 2,000,000,000; funds exceeding storage capacity stay verified and unallocated for reconciliation.

Another customer's claim is retained separately and flags ownership without changing the original subscriber or revoking approved access. An administrator must contact the sender number verified from the receiving account, record the intended subscriber and explain the resolution. An unverifiable payer or unclear shared phone leaves funds unallocated for official provider escalation. Allocated money cannot be assigned to another request.

Admin review uses server-side search and 30-request pages, with oldest open requests first. It supports individual receipt checks, approval and next, correction, rejection with a reason, disputes and an unallocated-funds filter. Revision checks and account/settings locks serialize reviewers. Audit events are append-only. The existing admin badge and customer inbox provide in-app updates. New checkout actions do not enqueue outbound SMS, WhatsApp or email. Optional support links let the customer open the relevant app with a request reference.

Private evidence follows the existing screenshot retention setting after approval, and seven days after rejection/cancellation. Disputed and verified-unallocated evidence remains available for reconciliation. Account erasure removes customer evidence and releases reservations. Permanent deletion is refused for accounts with receipt accounting; the operator can erase personal data instead. Number changes require open payment accounting to be resolved first.

## Release

1. Back up the database and pause writers while changing CHECK constraints.
2. On MySQL, apply the committed Prisma migration through the existing deployment workflow. On production MariaDB, import `prisma/mariadb/20261101120000_payment_checkout.sql` instead; it records the canonical migration checksum after verification.
3. Apply `docs/deployment/payment-checkout-grants.sql`, replacing the database and application principal placeholders.
4. Generate the Prisma client and deploy the application together. Run database health/schema checks before reopening writers.

The existing `/api/account/payments` URL now shares the authorised durable checkout handler. Cached older forms must refresh; they cannot create unreserved legacy submissions. Existing historical reports remain reviewable. Their approval requires explicit verification and registers their receipts in the shared uniqueness ledger.
