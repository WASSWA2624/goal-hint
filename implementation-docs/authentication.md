# Authentication and member access

## Purpose and scope

Goal Hint uses one phone-and-password sign-in for members and configured administrators. Members manage their profile, devices, and records from Account. [Subscriptions](subscriptions.md), [Payments](payments.md), [Wallet and referrals](wallet-and-referrals.md).

## Current implementation

- Public registration takes a mobile number and an 8–128 character password. The form shows the full country-coded number for confirmation before submitting the registration. The server normalizes and validates the number, rejects duplicates and reserved administrator numbers, and stores a salted scrypt hash. One transaction creates the account, records admission and eligible referral attribution, optionally grants a trial, and issues the session. Signup reads attribution from the signed invitation cookie. [Referral attribution and reward eligibility](wallet-and-referrals.md#invitations-and-reward-eligibility).
- New registrations receive ordinary account access immediately. `memberAdmittedAt` records admission, while `phoneVerifiedAt` records proof of number ownership. Either gives ordinary account admission. Referral-code exposure still requires phone verification. An admitted, unblocked member session gets full content access while Paid Access is off. When it is on, the server checks issued entitlement, including any eligible trial dated from original account creation. Signup sends no activation message.
- The signed-out account form handles login, registration, existing-code verification, recovery and reset. Account checks identity independently of subscription settings. Login and Register controls can open while public support contacts load, and a verified member sees the Account workspace while the requested section loads. A failed or overdue identity check offers a document retry at the same Account URL. This state exposes only the public shell until identity can be confirmed. Authentication stays available when subscription sales are off.
- The published Android app uses the same production Account screens and session routes in its embedded WebView. Account pages on the configured origin stay inside that view, and supported external recovery links can open the device’s messaging app. The signed APK rollout verified a cold launch into live Matches. Separate release checks cover the authenticated web flows. [Native navigation policy](../flutter/lib/web/navigation_policy.dart), [Android release verification](deployment-and-version-control.md#native-app-downloads), [authentication verification](deployment-and-version-control.md#authentication-rollout).

## End-to-end flows

| Flow | Server behavior |
| --- | --- |
| Register | `POST /api/account/register` validates the form, creates an admitted account, and starts an eligible trial. It issues a session and opens Matches, including for registrations started from checkout or a shared slip. A concurrent duplicate resolves to the existing-account conflict. Signed-in account creation is refused. |
| Sign in | `POST /api/account/login` checks the password and account state, then issues an opaque token. `/api/account/sign-in` is a compatibility alias and requires the same credentials. Login uses the previous cookie only for rotation during the successful session transaction. The browser sends one request at a time with a 15-second deadline and uses distinct feedback for credential refusal, throttling, connection failure, timeout and service unavailability. A timed-out login requires a manual retry. Members land on Matches by default. Explicit shared-slip and checkout journeys retain their validated destination. Administrators land on Admin by default and can keep an authorized review return path. A legacy account with a password and no admission enters restricted verification. |
| Check session | `GET /api/account/session` verifies the cookie and returns identity, administrator status, applicable subscription summary, and access flags for navigation. Protected page and API operations verify on the server. A request without a valid ordinary session cannot use member writes. Public access uses the policy described in [Subscriptions](subscriptions.md). |
| Sign out | The shared form closes the account menu and sends one navigation POST to `/api/account/sign-out`. The departing page clears its in-memory identity, switches to the guest header and cancels older session reads while the request is pending. The server revokes the current session, clears the cookies and redirects to Matches. The Flutter host gives native alert cleanup a bounded wait before submitting the form. During a storage failure the endpoint clears the local cookies and redirects to Login with a revocation warning. The dashboard routes use the same outcome. The Account devices action posts to `/api/account/devices` and revokes all other sessions after rechecking the current one. In Admin → Users, **Log out devices** revokes selected active sessions for the selected account, or all of the account's sessions via the existing all-devices option. |
| Change password | `POST /api/account/password` requires an ordinary session and matching `password` and `confirm` values. The signed-in change accepts a nonempty password up to 128 characters, including repeated characters and reused passwords. The transaction invalidates outstanding verification codes, revokes account sessions and issues a replacement to the current device. |
| Request recovery | Forgot password opens a dialog from Login. `POST /api/account/forgot` accepts the registered phone and reports whether a request was created or already exists. The dialog displays configured call, WhatsApp and SMS support links. Unknown, blocked, erased and reserved numbers receive matching acknowledgements without creating an admin request. |
| Review recovery | Admin → Password Requests opens the verified owner workspace before requesting the queue and any selected record. Each read has its own loading and retry state. A temporary queue failure stays in the queue pane, and an independently verified record stays available. A definitive session rejection clears the private panes and reset draft. An authorized administrator confirms control of the registered phone, generates or replaces a link, and can reopen its draft until expiry. Copy, SMS and WhatsApp provide manual delivery options. **Mark as Sent** records the administrator’s declaration, channel and time. The request remains **Link Generated** until completion or expiry. |
| Start or resume recovery for a user | In Admin → Users, the selected account's **Reset password** footer action finds or opens an eligible request using the account ID. It opens the existing Password Requests workflow. The administrator verifies control of the registered number there before generating the link. The user sets their password through the single-use link. |
| Reset a password | The reset page reads the secret from the URL fragment and sends it in same-origin POST bodies to `/api/account/password-reset/validate` and `/api/account/password-reset/redeem`. It can be opened repeatedly for 24 hours. A successful password change consumes the link in the same account-locked transaction, restores phone proof if needed, invalidates verification codes and revokes all account sessions. The user returns to Login. Expired, replaced and used links lead to a new request. Previously issued codes and reset-only cookies still use `/api/account/reset-code` and `/api/account/reset` until their original expiry. |
| Verify a legacy account | `POST /api/account/verify` consumes a previously delivered account verification code under a restricted session and records phone ownership. The `/api/account/verification` request endpoint directs users to an existing code or Forgot password. It sends no new account-verification messages. |
| Change phone | `POST /api/account/phone` checks the current password and validates the replacement number, then checks uniqueness and reserved numbers under lock. Changing to a different number clears previous phone proof, admission and WhatsApp update consent, revokes existing sessions, and opens recovery to prove the replacement. The account ID and its holder records stay with the member. |

## Account workspace and notices

- The Account section and formatted phone appear in the desktop sidebar and mobile section menu. Account defaults to Overview, with Subscription, Wallet, Referrals, Payments, Phone, Password, Devices, Notifications, and Activity available from the workspace. Each section has an accessible heading. Overview shows access and sign-in facts. Subscription shows the current and queued packages and links to checkout or an existing payment where applicable. Devices identifies the current session. [Account routing](../next-js/src/app/_components/account-route.tsx), [workspace](../next-js/src/components/members/account-workspace.tsx).
- Wallet and Referrals show balances, recent records and permitted actions. Payments searches and filters the loaded records. Activity is a separate read-only summary of up to ten recent payment, access, and referral events. The shared record workspace preserves the selected record and offers a mobile Back action. [Wallet and referrals](wallet-and-referrals.md), [payments](payments.md), [activity service](../next-js/src/server/members/account-dashboard.ts), [record workspace](../next-js/src/components/members/account-records.tsx).
- Notifications is a private inbox for an admitted or phone-verified ordinary member with a current session. The header and Account section show unread counts. Opening a notice leaves its unread state unchanged. Members can mark one or all as read, dismiss notices, or follow links to Payments, Subscription, or Referrals. The list shows up to 20 notices per page across a 90-day window and refreshes quietly while visible. [Notifications UI](../next-js/src/components/members/account-notifications.tsx), [notification service](../next-js/src/server/members/account-notifications.ts).
- The service reconciles payment decisions, access activation, approaching expiry, expired access, and referral earnings. Review transitions issue private notices for the affected holder. The expiry reminder uses the effective continuous end of access and starts one hour before it. A new access period can withdraw a stale reminder. The Notifications page exposes in-app inbox actions. The separate preferences endpoint handles retained WhatsApp consent. `members:notifications` and `members:renew` can reconcile notices without relying on a member visit. Live maintenance can also trigger reconciliation. [Notification rules](../next-js/src/domain/account-notifications.ts), [preferences endpoint](../next-js/src/app/api/account/preferences/route.ts), [member maintenance](../next-js/src/workers/members.ts), [notification tests](../next-js/tests/account-notifications.test.mjs).

## Rules and edge cases

- The cookie is `goal-hint-member`, with the `__Host-` prefix and `Secure` in production. It is host-only, `HttpOnly`, `SameSite=Lax` and scoped to `/`. The browser receives a 32-byte random token encoded as base64url. The database stores its SHA-256 hash. The ordinary cookie lasts up to 400 days and the underlying session expires after 90 days of inactivity. Verified use refreshes the server timestamp at most once per 24 hours without reissuing the cookie. The reset cookie and row expire after 15 minutes.
- Accounts have two concurrent authenticated sessions. A third successful login evicts the oldest other login, ordered by authentication time, creation time and token hash. Same-browser login rotates that token, keeping the other device when the account is within the cap. Unauthenticated verification/reset rows have a separate overall cap of ten session rows and do not evict authenticated devices. Blocked and erased accounts cannot sign in. A blocked identity may still have an existing session, while protected actions and entitlements check the blocked state.
- Auth writes require same-origin requests and accept only bounded, permitted fields. Read and write responses use private, no-store headers. Invalid input returns `400`, bad credentials or codes `401`, cross-origin writes `403`, conflicts such as duplicate signup `409`, throttles `429` with `Retry-After`, and unavailable services `503`. Sign-in errors use one generic credential message. Authentication service setup resolves the account database and session service without fetching subscription settings or checkout. Registration still reads trial eligibility in its own transaction. [Authentication services](../next-js/src/server/members/member-http.ts), [sign-in handling](../next-js/src/server/members/member-auth-http.ts).
- Login allows 30 attempts per address and 10 per phone per 15 minutes. Its `Retry-After` reports the remaining time in the exhausted window. Recovery requests allow 30 per address and 10 per phone per hour. An account has at most one pending or active-link request. Link validation permits 60 checks per address per 15 minutes. Redemption permits ten attempts per address and ten per account per 15 minutes. Legacy code checks retain their separate attempt limits. Fixed-window counters use keyed identifiers. Unresolved addresses share a bucket. Registration applies validation and uniqueness without a registration-attempt quota.
- Reset link lookups use a keyed digest. The current secret is encrypted for authorized retrieval and bound to the request, account and generation. The fragment stays out of HTTP URL logs and is removed from the page URL when read. The link landing page is skipped by visitor analytics and sends no referrer. Admin reads and writes require the existing privileged session. Replacing a link invalidates the previous secret immediately. Password or phone changes and account restrictions invalidate outstanding recovery authorizations.
- Password change and reset completion share a 24-hour cooldown after a password change. Both accept matching nonempty passwords up to 128 characters without a composition rule. Signup and previously issued code recovery retain the 8–128 character requirement. Phone changes also wait for the cooldown when switching numbers. Password changes and current-password checks have separate account-level attempt limits.
- The server uses `GOAL_HINT_ADMIN_PHONES` and `GOAL_HINT_ADMIN_PASSWORD` for privileged sign-in. The first successful administrator login can provision its account. Admin and Analytics dashboards require a current allowlisted, unblocked member session with the matching credential version, using the same login form. Existing ordinary sessions cannot gain privilege through an allowlist change. Credential rotation invalidates existing privileged sessions. Legacy admin login paths redirect to shared login. Admin passwords are managed through server configuration.

## Community invitations

- The public shell can show an invitation after the session check when Community is enabled and at least one visible WhatsApp destination has a configured URL. The invitation waits for the page to be visible and for the shared automatic dialog slot. Community remains available on demand from navigation. Invitations are limited to one per rolling 24 hours. Dismissing the invitation or answering No keeps the cooldown. [Invitation coordinator](../next-js/src/components/navigation/community-invitation-flow.ts).
- Opening a WhatsApp destination from the invitation records an attempt and closes the invitation. The originating browser asks “Did you join our community?” on return. Yes stores the user's confirmation and stops future reminders. A native WebView can also detect return at the user's next interaction when handing off to a device app leaves the page visible. [Return handling](../next-js/src/components/navigation/community-invitation-flow.ts), [production Community verification](deployment-and-version-control.md#community-invitations-production-verification).
- Guest choices use browser storage and can be lost when site data is cleared or the guest changes devices. After successful signup or login, a locally confirmed guest choice is applied to the authenticated account once. An account confirmation already on record is preserved. A signed-in account's confirmation and invitation cooldown follow it across devices.
- The private Community endpoint derives the account from the authenticated session. It checks same-origin requests and binds mutations to the current account and the matching invitation where applicable. Database updates prevent concurrent devices from claiming a second invitation inside the cooldown. Account erasure clears the retained Community fields. [Invitation UI](../next-js/src/components/navigation/community-invitation.tsx), [Account endpoint](../next-js/src/app/api/account/community/route.ts), [Migration](../next-js/prisma/migrations/20261126194240_community_invitations/migration.sql).

## Gaps and limits

- Public signup establishes the login claim for a valid unused phone number. Ownership usually comes later through successful recovery or a previously issued verification code.
- Recovery requires an available administrator and working support contact details. SMS and WhatsApp drafts depend on a compatible messaging app, and the administrator can copy the draft when a device cannot open it. A send declaration records an administrator’s action. Delivery depends on the external channel.
- The authentication return-path validator accepts numeric Best Slips ranks through 999. Canonical Best Slips links can represent higher ranks, which lose the direct return path through authentication. [Return-path validation](../next-js/src/domain/member-navigation.ts), [canonical rank parsing](../next-js/src/domain/best-slip-odds-bands.ts).
