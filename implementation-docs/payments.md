# Payments

## Purpose and scope

GoalHint accepts UGX payments for subscription packages and wallet top-ups. The subscription page guides an authenticated member through checkout and shows existing requests. The server owns the quote, receipt accounting, verification, and access handoff. [Subscription page and return routing](../next-js/src/app/_components/subscribe-route.tsx), [checkout interface](../next-js/src/components/members/checkout-flow.tsx), [member checkout API](../next-js/src/app/api/account/checkout/route.ts).

| Method | Eligible purchase | Verification |
| --- | --- | --- |
| Manual MTN Mobile Money or Airtel Money | Active package, optionally combined with wallet credit or earned days, or wallet top-up | Member transfers to the configured receiving account and submits evidence. An administrator checks the incoming transfer. |
| Flutterwave Standard v3 Uganda Mobile Money | Full price of an active package | The application redirects to hosted checkout and verifies the transaction with Flutterwave. |
| Wallet credit or earned referral days | Fully wallet-funded package or separate earned-day redemption | Checkout allocates existing balances in the confirmation transaction. |

Providers are shown when their configuration and the sales rules allow them. Wallet top-ups require a configured manual receiving account. Existing requests can still be reviewed after sales close. Production sales require the paywall to be on, published Privacy and Terms notices, and an enabled support contact. Production Flutterwave also requires a public support contact with calls or WhatsApp enabled. [Sales readiness](../next-js/src/server/members/sales-readiness.ts), [checkout request and funding rules](../next-js/src/domain/checkout.ts).

## Manual checkout and reconciliation

1. Checkout uses **Package → Pay → Payment Details → Review**. The server quotes the active plan or top-up, validates funding and the receiving account, and signs a quote tied to the member and its details. Confirmation rechecks the quote and records the terms version, plan, price, duration, and receiving details. A changed quote requires fresh confirmation. Wallet-only and earned-day-only selections skip receipt collection. [Quote and confirmation](../next-js/src/server/members/checkout.ts), [evidence form](../next-js/src/components/members/payment-evidence.tsx).
2. For an external transfer the current checkout requires a pasted transaction message, a screenshot, or both, along with the transaction ID, amount and payer details. The server recomputes discrepancies and requires explicit acknowledgement when present. Screenshots are bounded and format-checked, and evidence submissions are rate-limited. Image hashes help detect identical copies. OCR and image similarity are evidence aids. [Checkout HTTP validation](../next-js/src/server/members/checkout-http.ts), [evidence rules](../next-js/src/domain/checkout-evidence.ts), [image preparation and OCR](../next-js/src/components/members/payment-ocr.ts).
3. The request enters `pending`. An administrator opens `/admin/payments`, compares the claim with the actual incoming transfer, records verified amount, recipient and receipt time, and records separate findings for flagged evidence before approval. Corrections can reopen evidence checks. A verified shortfall puts the request in `remaining` so the member can attach another receipt. Unresolved ownership puts it in `disputed`. Rejected requests release reserved credit and days, and expired 48-hour reservations require the member to reconfirm funding. Members can cancel or withdraw evidence where the request permits it. [Admin route](../next-js/src/app/(owner)/admin/payments/page.tsx), [review and verification](../next-js/src/server/admin/checkout-review.ts), [member request status and allocation](../next-js/src/server/members/checkout.ts).
4. Confirmation retries use a unique request key. The canonical receipt key is provider plus normalized transaction ID. A repeat from the same account restores its original request. A conflicting claim across accounts can enter ownership review without revealing the other member to the caller. Ownership resolution requires the verified sender and contact with that payer. An already allocated receipt cannot be reassigned through ownership review. The review API checks the row revision before writing so stale reviews can refresh and retry. [Checkout receipt handling](../next-js/src/server/members/checkout.ts), [owner decision rules](../next-js/src/server/admin/checkout-review.ts).

## Flutterwave hosted checkout

1. The member confirms the full package quote and supplies an email for the receipt. `POST /api/account/checkout` with `start-flutterwave` creates or reuses the local request, then requests a 30-minute Uganda Mobile Money checkout session using the member's registered phone. The checkout lease and request key coordinate retries. The server validates the returned mode-specific hosted URL before exposing it. [Checkout actions](../next-js/src/server/members/checkout-http.ts), [provider client](../next-js/src/server/members/flutterwave.ts), [hosted initiation](../next-js/src/server/members/checkout.ts).
2. The browser return validates signed state for the local request and its allowed return destination. The webhook authenticates `verif-hash` against the private secret, checks the configured HTTPS endpoint, limits the request body and processes `charge.completed`. Both paths and the signed-in member's rate-limited `check-flutterwave` action use the same reconciliation. Return status can guide the interface for abandoned or cancelled returns. Independent provider verification decides the stored payment result. [Browser return route](../next-js/src/app/api/payments/flutterwave/return/[reference]/route.ts), [webhook route](../next-js/src/app/api/payments/flutterwave/webhook/route.ts), [callback handlers](../next-js/src/server/members/flutterwave-http.ts), [return URL and state](../next-js/src/server/members/flutterwave-navigation.ts).
3. Reconciliation checks provider transaction ID, the local `tx_ref`, exact expected amount, UGX, and verified status. Verified `successful` applies once to an eligible account. Verified failures and cancellations close the request as `rejected` or `cancelled`. An unmatched or still-pending provider response leaves the result unconfirmed. An expired hosted link can display cancellation while the request remains eligible for later verified reconciliation. Provider calls have deadlines, and a temporary verification failure can be retried through the status check or provider callback. Finalized receipts and access are protected by transaction and uniqueness checks. [Reconciliation](../next-js/src/server/members/checkout.ts), [provider deadlines](../next-js/src/server/members/flutterwave.ts), [member status](../next-js/src/components/members/flutterwave-payment-status.tsx).

## Records, access and controls

- `PaymentSubmission` stores the request, funding, plan snapshot and status. `PaymentReceipt`, `PaymentReceiptClaim`, and `PaymentReceiptEvidence` distinguish the transfer, the claimant's report, and private evidence. `PaymentEvent` records actions and decisions. The legacy payment endpoint accepts typed transaction details with an optional screenshot stored in `PaymentScreenshot`. [Schema](../next-js/prisma/schema.prisma), [checkout migration](../next-js/prisma/migrations/20261101120000_payment_checkout/migration.sql), [Flutterwave migration](../next-js/prisma/migrations/20261113150000_flutterwave_checkout/migration.sql), [provider outcome migration](../next-js/prisma/migrations/20261122210000_flutterwave_outcomes/migration.sql), [legacy request parsing](../next-js/src/server/members/payment-http.ts).
- Approval allocates the verified receipts and applies wallet and earned-day changes in the transaction. `WalletEntry` records debits, top-ups and excess verified funds. A top-up credits the wallet. A package or earned-day redemption creates an `AccessCode` period that appends after existing active access. Relevant checkout events also create account-update records. The member can continue to a validated return destination once access is confirmed. [Access period creation](../next-js/src/server/members/access-codes.ts), [wallet ledger](../next-js/src/server/members/wallet.ts), [checkout transactions](../next-js/src/server/members/checkout.ts), [subscriptions and access](subscriptions.md).
- Private member routes enforce account/session authorization, same-origin mutations and per-account or client rate limits as applicable. Owner-only review and evidence routes enforce administrator authorization. Configure manual providers and support contacts through subscription settings. Flutterwave reads `GOAL_HINT_FLUTTERWAVE_SECRET_KEY` for server verification, `GOAL_HINT_FLUTTERWAVE_WEBHOOK_SECRET` for authentication, and `GOAL_HINT_FLUTTERWAVE_WEBHOOK_URL` for callback binding. The runtime accepts optional `GOAL_HINT_FLUTTERWAVE_PUBLIC_KEY` and `GOAL_HINT_FLUTTERWAVE_ENCRYPTION_KEY`. Hosted staging and local development use sandbox mode, and hosted production selects live mode. Hosted readiness requires endpoint and signing-secret configuration. [Member authorization](../next-js/src/server/members/member-http.ts), [owner review API](../next-js/src/app/api/admin/payments/[id]/route.ts), [runtime configuration](../next-js/src/server/config/runtime-policy.ts), [settings example](../next-js/.env.example).

## Implementation limits

- The current checkout implements receipt verification, correction and ownership reconciliation. The reversal control is limited to older payment records. The hosted integration implements checkout and confirmation, and has no provider refund or chargeback handler. [Legacy reversal guard](../next-js/src/server/members/access-codes.ts), [provider client](../next-js/src/server/members/flutterwave.ts), [webhook event handling](../next-js/src/server/members/flutterwave-http.ts).
- Code and test coverage can establish how the integration handles successful and unsuccessful verification. The repository's recorded sandbox handoff received a provider authorization error before payment completed. Current merchant availability, real collection, settlement and provider webhook delivery were not verified in this audit. [Checkout integration tests](../next-js/tests/checkout.integration.mjs), [callback tests](../next-js/tests/flutterwave-http.test.mjs), [dated rollout evidence](../APP_OVERVIEW.md).
