# Payments

## Purpose and scope

The checkout implementation handles UGX subscription purchases and wallet top-ups for eligible signed-in members. **Subscribe** hosts the package flow. **Account → Wallet → Top up** opens the **Add credit** flow on that page. The same checkout shows current requests and reconciles a confirmed purchase before access is granted. [Subscribe route](../next-js/src/app/_components/subscribe-route.tsx), [Account Wallet](../next-js/src/components/members/account-wallet.tsx), [member checkout API](../next-js/src/app/api/account/checkout/route.ts).

| Method | Eligible purchase | Verification |
| --- | --- | --- |
| Manual MTN MoMo or Airtel Money | Active package, with optional partial wallet funding, or a wallet top-up | Member transfers to the configured receiving account and submits evidence. An administrator checks the incoming transfer. |
| Flutterwave Standard v3 Uganda Mobile Money | Full price of an active package | The application redirects to hosted checkout and verifies the transaction with Flutterwave. |
| Wallet balance | Fully funded active package | Checkout debits the spendable balance and issues the period in one transaction. |
| Earned referral days | Separate redemption for access time | Checkout spends the selected available days and issues access time in one transaction. |

Packages are offered when an eligible external method is available or spendable wallet credit can cover the price. A manual provider needs its switch enabled, a valid receiving number and an account name. Checkout can show a disabled manual option with its configuration reason. A top-up requires an available manual receiver. New production purchases require Paid Access On, release-ready Privacy and Terms notices, and an enabled support contact. Live Flutterwave also requires a contact shown publicly with calls or WhatsApp enabled and a ready provider configuration. Separate earned-day redemption checks Paid Access On and available days. Existing requests can still be reviewed when new sales pause. [Sales rules](../next-js/src/server/members/sales-readiness.ts), [manual provider rules](../next-js/src/domain/subscription-settings.ts), [checkout quote validation](../next-js/src/server/members/checkout.ts), [wallet and referral workflows](wallet-and-referrals.md).

## Manual checkout and reconciliation

1. The member chooses a **Package** or top-up amount, then selects MTN MoMo or Airtel Money on **Pay**. The page shows the quoted amount to send, receiving number, registered name and copy control. For a package, **Use wallet balance** applies eligible credit and reduces the cash amount, or covers the entire price. **Redeem earned days** opens a separate redemption with the amount of access time to use. Wallet-only, earned-day and hosted purchases go directly from funding to **Review**. Compatible package requests with recorded earned days apply them as extra access time. [Checkout flow](../next-js/src/components/members/checkout-flow.tsx), [Pay step](../next-js/src/components/members/checkout-pay.tsx), [server allocation](../next-js/src/server/members/checkout.ts).
2. After the transfer, **Payment Details** accepts a pasted message, a screenshot or both, with the transaction ID, reported amount and payer phone. The claim uses the date extracted from evidence when available and records when submission time supplies it. OCR can fill fields for the member to check. The server validates evidence source, format and size, recomputes discrepancies, and requires acknowledgement of warnings. The browser can restore safe choices and steps after refresh. Unsubmitted messages and screenshots are held only in memory. [Evidence form](../next-js/src/components/members/payment-evidence.tsx), [validation and limits](../next-js/src/server/members/checkout-http.ts), [draft persistence](../next-js/src/components/members/checkout-draft.ts).
3. **Review** shows the funding breakdown and asks for confirmation. The server binds the quote to the account, current price, funding and receiver, then rechecks it on submission. Changed terms require a fresh confirmation. Submission records the plan, duration, price, receiver and accepted terms version. The request key makes repeated confirmation safe. The receipt key is the provider plus normalized transaction ID. Reuse on the same account points to its existing request. A competing claim can enter ownership review while protecting the other member's identity. [Member confirmation and receipt identity](../next-js/src/server/members/checkout.ts), [evidence rules](../next-js/src/domain/checkout-evidence.ts).
4. **Subscribe** and **Account → Payments** show submitted requests. A new manual report normally starts as `pending`. Requests can enter `remaining` for a verified shortfall, `correction` for evidence that needs replacement and `disputed` for unresolved ownership. The member can attach another receipt, withdraw incorrect evidence, cancel or reconfirm where allowed by status. Reserved wallet credit and days have a 48-hour window. Expired reservations can require `reconfirm` before allocation. Approval, rejection and cancellation record the outcome, and rejection or cancellation releases applicable unspent reservations. [Member request interface](../next-js/src/components/members/checkout-flow.tsx), [Account Payments](../next-js/src/components/members/account-payments.tsx), [request transition rules](../next-js/src/server/members/checkout.ts).

## Owner review

**Admin → Payments** opens the review queue and shows details for the selected request. The owner can search by reference, transaction or phone, and filter by status and manual provider. **Show More** appends up to 30 matching reports through the existing owner-only queue endpoint. A failed batch leaves the loaded queue and selected review available for retry. The review shows the reported and verified values, evidence, amount due and expected wallet credit. It also exposes part-paid, disputed and unallocated-funds views. **Approve and next** advances through loaded pending requests or opens the next pending request through the existing review link. [Payments route](../next-js/src/app/(owner)/admin/payments/page.tsx), [queue interface](../next-js/src/components/admin/payments-editor.tsx), [queue queries](../next-js/src/server/admin/payment-review.ts), [receipt review](../next-js/src/components/admin/checkout-review-view.tsx).

The owner compares manual evidence with the actual transfer and records verified amount, receiving account and time. Flagged evidence needs a review finding before allocation. Ownership resolution requires the verified sender and confirmation of contact with that payer. Allocated receipts retain their original destination. The review API checks the request revision, so a concurrent decision requires refreshing before another write. [Owner action API](../next-js/src/app/api/admin/payments/[id]/route.ts), [verification and decision transaction](../next-js/src/server/admin/checkout-review.ts).

## Flutterwave hosted checkout

1. The member chooses Flutterwave on **Pay**, confirms the full package quote on **Review** and enters a receipt email. `start-flutterwave` creates or reuses a local `provider-pending` request and asks for a 30-minute Uganda Mobile Money session using the account's registered phone. The request lease coordinates retries. The web page navigates to the validated hosted URL. The Flutter shell delegates off-origin hosted navigation to the device's browser and keeps the GoalHint page in its web view. [Checkout actions](../next-js/src/server/members/checkout-http.ts), [provider client](../next-js/src/server/members/flutterwave.ts), [native navigation](../flutter/lib/web/navigation_policy.dart).
2. The browser return validates signed state tied to the local request and allowed destination. The webhook authenticates `verif-hash` with the private secret, checks the bound endpoint, limits the body and handles `charge.completed`. Those routes and the signed-in member's **Check status** action share provider reconciliation. A browser cancellation or expired link can display recovery guidance while the stored request awaits independent verification. The status card offers a usable session link or retry when eligible. [Callback handlers](../next-js/src/server/members/flutterwave-http.ts), [return URL and state](../next-js/src/server/members/flutterwave-navigation.ts), [member status card](../next-js/src/components/members/flutterwave-payment-status.tsx).
3. Reconciliation checks provider transaction identity, local `tx_ref`, exact expected UGX amount and verified outcome. Verified `successful` allocates a receipt and issues one access period for an eligible account. Verified `failed` and `cancelled` map to `rejected` and `cancelled`. Unmatched or still-pending verification leaves the result unresolved. Request and receipt uniqueness protect retries. [Reconciliation and allocation](../next-js/src/server/members/checkout.ts), [provider call deadlines](../next-js/src/server/members/flutterwave.ts).

## Records, access and controls

- `PaymentSubmission` stores the request, funding, plan snapshot and status. `PaymentReceipt`, `PaymentReceiptClaim`, and `PaymentReceiptEvidence` distinguish the transfer, the claimant's report, and private evidence. `PaymentEvent` records actions and decisions. The legacy payment endpoint accepts typed transaction details with an optional screenshot stored in `PaymentScreenshot`. [Schema](../next-js/prisma/schema.prisma), [checkout migration](../next-js/prisma/migrations/20261101120000_payment_checkout/migration.sql), [Flutterwave migration](../next-js/prisma/migrations/20261113150000_flutterwave_checkout/migration.sql), [provider outcome migration](../next-js/prisma/migrations/20261122210000_flutterwave_outcomes/migration.sql), [legacy request parsing](../next-js/src/server/members/payment-http.ts).
- Approval allocates receipts, debits reserved funding, credits eligible excess funds and records the outcome in one transaction. A top-up credits the wallet. A package or redemption issues an `AccessCode` access period. Approved package checkout can return the member to the original feature through the validated path. [Checkout transactions](../next-js/src/server/members/checkout.ts), [access periods](../next-js/src/server/members/access-codes.ts), [wallet and referrals](wallet-and-referrals.md), [subscription access](subscriptions.md).
- Member endpoints enforce account/session authorization, check same-origin writes and apply rate limits where relevant. Owners alone can open review records and evidence attachments. Evidence retention removes eligible screenshots and claim content after the applicable retention period. Disputed receipts and verified unallocated funds retain their evidence. Financial relationships and unresolved provider sessions can block permanent subscriber deletion or erasure as applicable. [Member authorization](../next-js/src/server/members/member-http.ts), [owner evidence route](../next-js/src/app/api/admin/payments/[id]/screenshot/route.ts), [evidence retention](../next-js/src/server/members/purge.ts), [subscriber deletion](../next-js/src/server/admin/delete-subscriber.ts), [subscriber erasure](../next-js/src/server/admin/subscribers.ts).
- **Admin → Settings → Payments** and **Support** configure manual providers and public contact details. Flutterwave takes environment-specific private runtime settings. Hosted staging and local development select sandbox, while hosted production selects live. Hosted checkout readiness requires a mode-matched server key, the bound HTTPS webhook URL and its signing secret. Local sandbox checkout can be ready with a valid sandbox key and uses separately configured callbacks. [Settings editor](../next-js/src/components/admin/settings-editor.tsx), [runtime validation](../next-js/src/server/config/runtime-policy.ts), [environment keys](../next-js/.env.example), [hosted configuration runbook](../next-js/docs/deployment/how-to-deploy.md).

## Implementation limits

- The current checkout supports receipt verification, correction and ownership reconciliation. The admin reversal action applies to eligible legacy records. Provider-side refund and chargeback processing remains outside the hosted integration. [Legacy reversal guard](../next-js/src/server/members/access-codes.ts), [hosted provider client](../next-js/src/server/members/flutterwave.ts), [webhook event handling](../next-js/src/server/members/flutterwave-http.ts).
- Automated checks exercise provider decisions and signed callbacks. The recorded hosted sandbox test created a payment link and reached Flutterwave, which returned HTTP 403 before payment controls appeared. That attempt recorded no collection, provider-delivered webhook or access grant. Merchant approval, private configuration and a successful live collection are separate checks. Earlier manual-provider settings and sandbox outcomes describe their recorded environments and dates. [Checkout integration tests](../next-js/tests/checkout.integration.mjs), [callback tests](../next-js/tests/flutterwave-http.test.mjs), [recorded rollout and sandbox outcome](../APP_OVERVIEW.md).
